1Overview

ExportUtils is a top-level native AVM2 class that turns in-memory tabular data into a ready-to-save file, doing all the heavy work in Rust and handing back a flash.utils.ByteArray.

It reads straight over the raw data-provider structures already in memory — an Array of rows, or an XMLList — without forcing the caller to flatten or copy them first, and it streams the output so it stays usable on very large data sets (on the order of a million rows). The output format is selected per call; xlsx (a real OOXML workbook) and CSV are supported today, and the surface is designed so further formats can be added without changing the call sites.

Two execution models share the same configuration:

  • Synchronous — one call builds the whole file and returns the bytes.
  • Asynchronous — a chunked flow (begin / continue / end / cancel) that yields to the runtime between blocks, so a large export does not freeze the UI and a progress indicator can advance.
At a glance Everything travels through a single options object. Keys that do not apply to the chosen format are silently ignored, so the same call shape works across formats and both execution models.

2Resolving the class

ExportUtils lives in Ruffle's playerglobal, not in the stock Adobe one your SWF compiles against. Resolve it at runtime with getDefinitionByName and guard for the case where the SWF runs on a build (or a real Flash Player) that does not provide it: 

import flash.utils.getDefinitionByName;
import flash.utils.ByteArray;

function exportClass():Class {
    try {
        return Class(getDefinitionByName("ExportUtils"));
    } catch (e:Error) {
        return null; // not running on a build that provides ExportUtils
    }
}

All methods are static; the class is never instantiated. Because the SWF is compiled against the stock playerglobal, the compiler knows neither ExportUtils nor its members — so call them through dynamic bracket access on the resolved Class object (xport["syncExport"](…)), not dotted access (xport.syncExport(…)), which would fail to compile in strict mode. The examples below follow this pattern. (The handle returned by asyncExportBegin is a dynamic Object, so its __total/__done fields can be read with the dot syntax.)

3API surface

Five static methods: one for the synchronous path and four for the chunked one.

MethodReturnsPurpose
syncExport(rows, fields, header, options)ByteArray Build the entire file in one call and return the bytes.
asyncExportBegin(rows, fields, header, options)Object Start a chunked export; returns an opaque handle.
asyncExportContinue(handle)int Process one chunk; returns the cumulative number of rows done so far.
asyncExportEnd(handle)ByteArray Flush any remaining rows, finalise the file, return the bytes. Consumes the handle.
asyncExportCancel(handle)void Discard an in-progress export and release its state. Consumes the handle.

The handle returned by asyncExportBegin is a plain object carrying two read-only progress fields you can bind a UI to:

Handle fieldTypeMeaning
__totalintTotal number of rows to export.
__doneintRows processed so far (mirrors the return of asyncExportContinue).
Handle lifecycle A handle is single-use: once passed to asyncExportEnd or asyncExportCancel it is consumed and must not be reused. Always reach one of the two terminal calls (use try/finally around the loop) so the native state is released.

4Row sources & field selectors

Row sources

options.rows is either an Array or an XMLList. When it is an Array, each element may be:

  • an XMLReadOnly node (fastest — extracted with a zero-allocation path),
  • a mutable XML / E4X node, or
  • a plain object (fields read as public properties).

Pass the rows in whatever order you want them written — for a sorted/filtered grid, iterate the view (e.g. via ICollectionView.createCursor()) into an Array so the file reflects what the user sees.

Field selectors

options.fields is an Array with one entry per column, in column order. Each entry is a string that selects a value from the row, using the same mini-syntax as XMLReadOnly.sortKeyed:

SelectorSelects
""the row's own simple content (the node/value itself).
"@name"the attribute name (for XML/XMLReadOnly rows).
"name"the child element name, or the property name for plain objects.
null / undefinedan always-empty cell (placeholder column).
 
// Three columns: an attribute, then two child elements / properties.
var fields:Array = ["@id", "name", "amount"];

6Output formats

xlsx

A real OOXML workbook (a ZIP of XML parts). The worksheet is written one row at a time straight into the ZIP entry, with inline strings (no shared-string table), so peak memory stays flat regardless of row count. Multi-row grouped headers, per-column alignment, fonts, fills and borders are all supported (see §7).

Type auto-detection (xlsx)

Each column is typed independently by scanning a sample of the rows (the first typeSampleRows, default 1000; 0 scans all). A column becomes number or date only if every non-empty sampled value matches; otherwise it stays text. A value beyond the sample that no longer fits its column type is written as text for that single cell, so no data is lost. Set detectTypes:false to make everything text (forceText is CSV-only).

  • Number — an optional sign, digits, and at most one decimal separator (. or ,, always decimal, never a thousands separator); the integer part may be omitted (,332 → 0.332). Exponents (23456E1), leading-zero codes (007) and values over 15 significant digits stay text. Stored as a real number with the General format — integers show no trailing separator and the decimal separator follows Excel's locale.
  • Date — the exact form YYYY-MM-DD HH:MM:SS, stored as an Excel serial with a yyyy-mm-dd hh:mm:ss number format (sortable and filterable as a real date). Turn off with detectDates:false.
  • Text — everything else. Textual values that look numeric (codes such as 23456E1) would trigger Excel's “number stored as text” warning; the worksheet suppresses it over the data area with an <ignoredErrors> block.

CSV

UTF-8 with a BOM and CRLF line endings. There is no type detection in CSV — every value is written as text; how each cell is quoted depends on forceText:

  • Default (forceText:false) — RFC 4180 quoting: a field is wrapped in "…" only when it contains the separator, a ", or a line break, with any inner " doubled; otherwise it is written bare. A spreadsheet app may then still re-interpret a bare value that looks like a number or date.
  • forceText:true — every data cell is emitted as the formula string ="<value>", which forces verbatim text import (leading zeros, number/date-looking values, etc.). Because that formula is itself CSV-quoted, the literal output for a value V is "=""V""", and each " inside V becomes four. Header titles are not wrapped — they stay plain.

separatorHint prepends a sep=<separator> line so some spreadsheet apps adopt a non-standard separator. With compress, the CSV is wrapped in a single-entry ZIP archive (<sheetName>.csv), streamed through the same deflate path as xlsx.

7Headers & styling (xlsx)

With header = null (the default) xlsx writes a flat header row of field names, exactly like CSV. For grouped, multi-row headers, pass the header parameter as a small XML descriptor: <c> is a leaf column (must line up, in order, with fields) and <g> is a group spanning its children. The t attribute is the displayed title; textAlign (left/center/right) sets the column alignment and is propagated to the data cells of that column; width on a leaf sets its column width. 

var header:XML =
  <h>
    <c t="Region"/>
    <g t="Sales">
      <c t="Q1" textAlign="right"/>
      <c t="Q2" textAlign="right"/>
    </g>
  </h>;

var fields:Array = ["region", "q1", "q2"]; // one entry per <c> leaf, in order

Colours are 0xRRGGBB uints: headerBackgroundColor / headerForegroundColor style the header cells, and rowBackgroundColors:[even, odd] paints alternating data rows (populated cells only). A thin black border is drawn around every cell inside the populated area.

8Synchronous export

Build the options, call syncExport, and hand the bytes to whatever save mechanism your app uses (FileReference.save shown here as a generic example): 

import flash.net.FileReference;
import flash.utils.ByteArray;

var xport:Class = exportClass();

// rows: an Array you collected from your data provider, in display order.
var bytes:ByteArray = xport["syncExport"](
    rows,                                  // row source, in display order
    ["@id", "name", "amount"],             // fields
    <h>
      <c t="ID"/>
      <c t="Name"/>
      <c t="Amount" textAlign="right"/>
    </h>,                                 // header (null -> flat header from fields)
    {
        format: "xlsx",
        headerBackgroundColor: 0x4F81BD,
        headerForegroundColor: 0xFFFFFF,
        rowBackgroundColors:  [0xFFFFFF, 0xEEF3FA]
    }
);

new FileReference().save(bytes, "export.xlsx");

A minimal CSV variant:

var csv:ByteArray = xport["syncExport"](
    rows,
    ["@id", "name", "amount"],
    null,                                  // no header in CSV
    { format: "csv", separator: ";", forceText: true }
);
new FileReference().save(csv, "export.csv");
When to prefer async syncExport runs to completion in a single call and blocks the runtime meanwhile. For large data sets (tens of thousands of rows and up) this can freeze the UI for several seconds — use the chunked API below so the player can repaint.

9Asynchronous (chunked) export

The chunked flow splits the work across many short calls. You drive it from a loop that yields to the runtime between calls — typically an ENTER_FRAME handler or a zero-delay Timer — so the player gets a frame to repaint (and a progress bar to advance) between blocks. 

import flash.events.Event;
import flash.net.FileReference;
import flash.utils.ByteArray;

var xport:Class = exportClass();
var handle:Object = xport["asyncExportBegin"](
    rows,
    ["@id", "name", "amount"],
    <h><c t="ID"/><c t="Name"/><c t="Amount"/></h>,
    { format: "xlsx" }
);
var total:int = int(handle.__total);

// `driver` is any DisplayObject on the stage. Weak listener — see Gotchas.
driver.addEventListener(Event.ENTER_FRAME, onTick, false, 0, true);

function onTick(e:Event):void {
    var done:int = xport["asyncExportContinue"](handle);
    progressBar.setProgress(done, total);          // update your UI
    if (done >= total) {
        driver.removeEventListener(Event.ENTER_FRAME, onTick);
        var bytes:ByteArray = xport["asyncExportEnd"](handle);
        new FileReference().save(bytes, "export.xlsx");
    }
}

To abort early (e.g. a Cancel button), stop the loop and release the state:

driver.removeEventListener(Event.ENTER_FRAME, onTick);
xport["asyncExportCancel"](handle);
Throughput vs. smoothness The default chunk is 1% of the rows, so the export yields ~100 times — smooth progress at a small overhead (one frame per chunk). Raise minChunkSize, or process several chunks per frame, to trade progress granularity for speed.

10Performance & memory

The writer is a hand-rolled ZIP container (local headers + central directory) whose entry payload is produced with a raw deflate stream. Rows are serialised and compressed incrementally into a small fixed scratch buffer and appended to the output, so peak memory is governed by the output size, not by an intermediate full-document buffer — the export scales to ~1M rows where an all-in-RAM writer would not.

In the asynchronous path the per-export state is kept across calls on the Rust side; each asyncExportContinue does work proportional only to the rows in that chunk, so total cost stays linear in the number of rows. Cell extraction has a zero-allocation fast path for XMLReadOnly rows, which is the cheapest source for large data sets.

11Notes & gotchas

  • Always finish or cancel. The async handle holds onto the row source until asyncExportEnd / asyncExportCancel runs. Wrap the loop so one of them is always reached, even on error.
  • Weak listeners for the driver. If you drive the loop from a listener (or a closure) that captures the surrounding scope, register it with useWeakReference = true — or remove it in a terminal branch. A strong listener on a long-lived object keeps the captured scope (and, with it, the rows array) alive after the export is done. In ActionScript a closure captures its whole enclosing activation, not just the variables it names.
  • Row order is yours. Rows are written exactly in the order you pass them. To honour the on-screen sort/filter of a collection, iterate its view cursor into the array rather than reading the backing list.
  • Type detection is per column and conservative. A column is numeric or a date only when every non-empty sampled value fits; one non-matching value within the first typeSampleRows keeps the whole column textual. Numbers accept a comma or dot decimal and an omitted integer part (,332) but reject thousands separators, exponents and leading-zero codes. Use detectTypes:false to force plain text (xlsx); forceText is CSV-only.
  • Excel has no “typed columns”. A cell's type follows its stored value, not a column declaration: editing a numeric cell to non-numeric content just turns it into text (dropped from sums), with no error. The green triangle is only Excel's heuristic for text that looks numeric — suppressed here by design — not a type-integrity check.
  • Grid cap. The xlsx grid is limited to 1,048,575 data rows; extra rows are dropped.
