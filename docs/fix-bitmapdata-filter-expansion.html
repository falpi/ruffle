BitmapData.generateFilterRect (AVM1 + AVM2) and the region BitmapData.applyFilter writes (wgpu backend). Display-object filters (DisplayObject.filters) are untouched — they already render into pre-expanded offscreen surfaces.

Every default Flex tooltip renders in Ruffle without its drop shadow, and with a squarish bottom edge instead of the rounded one Flash Player shows. The shadow is not a display-object filter: Flex pre-renders it through BitmapData.generateFilterRect + applyFilter and copies it in slices. generateFilterRect was a stub in Ruffle, so the slice thicknesses came out as zero and the shadow silently vanished. This document explains the Flex mechanism, the two independent gaps in Ruffle that both had to close, and how the fix keeps the two APIs mutually consistent by construction.

1The symptom

Compared side by side with Flash Player, the default mx.controls.ToolTip in Ruffle is missing two things at once: the soft drop shadow below and beside the yellow face, and the visibly rounder bottom corners. Both are the same pixels. The tooltip face is drawn with cornerRadius = 2; the "rounded bottom border" seen in Flash Player is the shadow, drawn with radius cornerRadius + 2 and offset 3px downwards, hugging the bottom edge. Lose the shadow and both effects disappear together — silently, with no error and no visual artifact other than absence.

The only runtime trace was a stub warning in the console: flash.display.BitmapData.generateFilterRect is a stub.

2How Flex draws a tooltip shadow

2.1 The skin pipeline

The tooltip skin is mx.skins.halo.ToolTipBorder — also under the Flex 4 Spark theme, because the framework's defaults.css assigns it (borderSkin + borderStyle: "toolTip") and the Spark theme does not override the ToolTip selector. For the default "toolTip" border style the skin draws the face, then delegates the shadow: 

// mx.skins.halo.ToolTipBorder, borderStyle "toolTip"
drawRoundRect(3, 1, w - 6, h - 4, cornerRadius, backgroundColor, backgroundAlpha);

dropShadow.distance = 3;   dropShadow.angle = 90;
dropShadow.color    = 0;   dropShadow.alpha = 0.4;
dropShadow.tlRadius = dropShadow.trRadius =
dropShadow.blRadius = dropShadow.brRadius = cornerRadius + 2;
dropShadow.drawShadow(graphics, 3, 0, w - 6, h - 4);

Note what this is not: it is not filters = [new DropShadowFilter(…)] on the display object. For performance, Flex pre-renders the shadow once into bitmaps and tiles it with beginBitmapFill, so that animating or moving the tooltip never re-runs the filter.

2.2 RectangularDropShadow

mx.graphics.RectangularDropShadow.createShadowBitmaps() is where both Ruffle APIs enter the picture:

  1. It draws a small white round rectangle into a scratch BitmapData — just large enough to carry the four corner radii.
  2. It asks generateFilterRect(inputRect, filter) how far a DropShadowFilter(distance=3, angle=90, blurX=4, blurY=4) expands that rectangle, and derives the shadow thickness on each edge by difference: leftThickness = inputRect.left − outputRect.left, and so on for right, top, bottom.
  3. It allocates the shadow bitmap at the expanded size, and calls applyFilter(…, new Point(leftThickness, topThickness), filter) with knockout = true, so the bitmap contains only shadow, transparent where the face will sit.
  4. It cuts four 1px strips (left/right/top/bottom edges) out of the result. drawShadow() then tiles corners and strips around the face with beginBitmapFill — every copy guarded by the strips existing: if (leftShadow || topShadow) { … }.

3The two gaps in Ruffle

3.1 generateFilterRect was a stub

In AVM2 the method lived in ActionScript (BitmapData.as) and returned sourceRect.clone() after logging a stub warning, with one special case already handled (Flash reports the entire bitmap for a ShaderFilter). In AVM1 it was an avm1_stub! returning undefined. Either way: no expansion, thicknesses zero, shadow gone — see Figure 1.

3.2 applyFilter clipped its output to the source rect

Independently, the wgpu backend rendered every applyFilter into an intermediate texture the size of the source rect (each filter's target is created at source.size) and copied that to the destination at destPoint. Pixels a filter produces beyond the source rect — blur margins on all sides, the drop shadow's distance offset — were never rendered at all. A pre-existing FIXME in core/src/bitmap/operations.rs acknowledged exactly this.

Flash's semantics are different: destPoint is where the top-left corner of the source rect lands in the destination, and the filtered output is written around it, covering the full generateFilterRect region. RectangularDropShadow depends on this: it slices its strips precisely from those beyond-the-source pixels.

3.3 Why the halves only work together

Hazard Fixing generateFilterRect alone would have made things worse. The shadow bitmap is allocated at the expanded size with the BitmapData default fill — opaque white. If applyFilter then only writes the source-rect region in its middle, the perimeter — exactly the region the strips are sliced from — keeps its initial fill, and the tooltip gets tiled with opaque white bars instead of no shadow. The report and the write must expand by the same amount, in the same release.

4The fix

4.1 One source of truth: calculate_dest_margins

Ruffle already had a filter-expansion estimate — Filter::calculate_dest_rect, used to size the offscreen surfaces of display-object filters — but it is deliberately generous (its blur pass scaling is documented as "very approximate to Flash"). That is harmless for an offscreen size and wrong for applyFilter, where the margins define exactly which destination pixels get replaced. The fix adds a separate, exact method and makes both halves of the API consume it: 

/// How far a filter's output extends beyond the source image
/// on each edge, in pixels.
pub struct FilterMargins { pub left: u32, pub top: u32, pub right: u32, pub bottom: u32 }

impl Filter {
    /// `BitmapData.generateFilterRect` reports this expansion and
    /// `BitmapData.applyFilter` writes it, so both must use this method.
    pub fn calculate_dest_margins(&self) -> FilterMargins { … }
}

The per-filter values follow Flash Player, measured from Flash-captured test goldens (§7): a blur of strength b with q passes reaches ceil((b − 1) · q / 2) pixels per side (blur 4 quality 1 writes exactly 2 pixels beyond the source rect); a drop shadow adds its distance offset, ceiled, on the side it points towards (inner shadows and inner glows don't expand at all); a bevel adds the offset on both sides. calculate_dest_rect and the display-object pipeline are untouched. Consistency between "what we report" and "what we write" is structural rather than a convention to maintain.

4.2 Native generateFilterRect (AVM2 + AVM1)

The AVM2 method became a native function; the Rust side (generate_filter_rect in bitmap_data.rs) converts the filter with the same Filter::from_avm2_object that applyFilter already uses, floors/ceils the source rect to whole pixels with the same rules as applyFilter's source_point/source_size, applies the margins, and builds the result via the (previously private, now pub) new_rectangle helper. The ShaderFilter special case — Flash reports the whole bitmap, ignoring sourceRect — moved from ActionScript into the native method unchanged. The AVM1 stub got the same implementation on top of the same helper, returning a flash.geom.Rectangle through the AVM1 constructor.

For the tooltip's filter (blur 4×4 at quality 1, distance 3 at 90°) the margins come out as 2px on left/right/top and 5px on the bottom — the blur reach on every side, plus the distance offset only on the side the shadow moves towards.

4.3 Padded filtering in the wgpu backend

WgpuRenderBackend::apply_filter now pads before it filters, reproducing two more pieces of Flash semantics that the goldens revealed (§7): a blur samples real source pixels beyond the source rect (as long as they exist in the source bitmap), and beyond the bitmap's physical bounds everything is transparent (not edge-replicated, as the old UV clamping effectively did).

  1. Compute margins = filter.calculate_dest_margins(). If they are all zero (e.g. a color matrix), the previous code path runs unchanged.
  2. Create an intermediate texture of the padded size. For a blur, the padding is doubled — a write ring plus a sampling ring — and the copy from the source texture covers the source rect grown by the whole padding, clamped to the bitmap's bounds: the written margins blur real neighbor pixels, exactly like Flash. For filters that composite the source over their output (glow, drop shadow, bevel) the copy covers the source rect only — neighbor pixels in the padding would get painted into the margins — so their padding stays transparent. Whatever the copy doesn't cover stays transparent, because wgpu zero-initializes textures.
  3. Run the filter over the entire padded texture (FilterSource::for_entire_texture). Blur spreads into the margins; the drop shadow's offset lands inside them instead of being clipped.
  4. Copy the write region (padded output minus the sampling ring) to the destination at dest_point − (margins.left, margins.top). The existing clamping already handles the now-possibly-negative destination coordinates.

Guards: padding is skipped when the margins are empty or when the padded texture would exceed max_texture_dimension_2d (pathological blur/source combinations), falling back to the old behavior instead of panicking. The intermediate uses the source texture's own format, so the texture-to-texture copies are always format-compatible.

5Fidelity and behavior notes

  • Margins are Flash-exact, measured from goldens. The blur write reach ceil((b−1)·q/2) was validated pixel-by-pixel against Flash Player captures: the bitmapdata_filter_sourcerect test — previously allowed 1700 outliers with a "way off here compared to FP" comment — now passes with zero outliers (max channel difference 2). The generous calculate_dest_rect stays in place for display-object filter bounds, where over-estimation is harmless.
  • Bitmap-edge semantics changed, matching Flash. The old code sampled the source via UV coordinates with a clamping sampler: beyond the bitmap's physical edge it replicated edge pixels. The Flash goldens show a fade instead — beyond the bitmap is transparent. In-place full-bitmap blurs (blur_quality-style content) now fade at the edges like Flash instead of staying saturated.
  • applyFilter now writes a larger region. Flash-correct, but content that previously "got away" with the clipped output will now have its destination pixels replaced in the expanded ring too (replacement, not blending — same as before, over a bigger area).
  • 0×0 source rects are still a noop. In Flash a filter on an empty source can still emit its expansion; the early-return in operations.rs is kept (it also protects the CPU fallback path from zero-sized regions) and its FIXME comment narrowed to this remaining case.
  • Unsupported-filter fallback unchanged. Filters the backend rejects (is_filter_supported false, e.g. gradient glow) never reach the padding code — core still degrades them to a plain copy.

6Impact and coverage

In the Flex framework the mechanism this restores is used by:

  • mx.skins.halo.ToolTipBorder — every default tooltip, under both Halo and Spark themes (shadow + the rounded-bottom look);
  • mx.preloaders.DownloadProgressBar and SparkDownloadProgressBar — the preloader panel shadow.

Beyond Flex, any AVM1/AVM2 content that calls generateFilterRect (previously getting a useless echo of its input) or relies on applyFilter writing blur margins or shadow offsets outside the source rect now gets Flash-compatible behavior. Display-object filters are unaffected: that pipeline already expanded its offscreen surfaces via the same calculate_dest_rect.

7Testing

The first iteration of this branch (margins derived from the approximate calculate_dest_rect, transparent-only padding) failed six CI tests. The failures were diagnosed by sampling the Flash-captured golden images pixel-by-pixel, which produced the three measured facts the final design is built on: the exact blur write reach (bitmapdata_filter_sourcerect: a 104×104 written region for a 100×100 rect with blur 4 quality 1); real-neighbor sampling beyond the source rect (same golden: a solid, full-strength ring around the block, and red bleeding into black across the rect's edge); and transparency beyond the physical bitmap (bitmapdata_applyfilter_destpoint_edges: a gradual fade outside the bitmap, where edge replication would stay saturated).

  • avm2/bitmapdata_filter_sourcerect (true Flash golden): passes with 0 outliers, max channel difference 2 — down from the 1700-outlier allowance the old behavior needed ("FIXME We're way off here compared to FP").
  • bitmapdata_applyfilter_destpoint / _colormatrix (AVM1 + AVM2): pass unchanged.
  • avm2/bitmapdata_applyfilter_destpoint_edges: still known_failure (it includes an unsupported ConvolutionFilter); its Ruffle-canonical output.ruffle.png was regenerated for the new, closer-to-Flash output.
  • Regenerated Ruffle-canonical goldens: bitmapdata_applyfilter_blur, visual/filters/blur_quality, visual/filters/blur_fractional, away3d_advanced_shallow_water_demo. Their previous output.expected.png files encoded the old no-expansion / edge-replication behavior: their git history shows they were regenerated for unrelated Ruffle rendering changes (e.g. device-font spacing) — a Flash capture would never change for those.
  • gnash BitmapData-v8 (AVM1): only asserts the method exists — no output changes.
  • Build checks: cargo check, clippy and cargo fmt clean on the touched crates.
  • Visual verification (Flex app under the Electron shell): tooltip shadow and rounded bottom edge restored; watch for regressions around other applyFilter call sites, since they now legitimately write a larger region (§5).
