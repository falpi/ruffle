1Motivation

Ruffle's mutable XML type stores every node as its own Gc allocation (an E4XNode wrapping E4XNodeData). On XML-heavy workloads the node tree is the dominant memory consumer, and shaving bytes off the per-node record scales by tens of millions of nodes.

This branch applies six independent, behavior-preserving refinements to that record. They are all internal representation changes: the E4X/XML public API and observable semantics are unchanged, there is no unsafe, and each was validated A/B on a data-oriented workload. The refinements fall into two groups by what they shrink:

  • The node (E4XNodeData, paid by every node) — BOXED separates it from the element payload, then INTERN and RARE-FIELDS shrink it.
  • The element payload (E4XElementData, paid only by elements) — LAZY-NS, LAZY-ATTR and CHILDREN-ENUM shrink it step by step.
Net result Measured end-to-end on a 250k-row workload, the six refinements take total live memory from 1425.6 MB to 774.6 MB — −651 MB (−46%), all with zero unsafe and an unchanged API.

2Anatomy of an E4X node

An E4XNode is a Gc handle to an E4XNodeData. The data record holds the fields shared by all node kinds — parent link, local name, and the kind — where kind is an E4XNodeKind enum: leaf kinds (Text, CData, Comment, Processing Instruction, Attribute) carry just an AvmString, while the Element kind carries the attribute, child and namespace lists.

3What drives the footprint

Each node is its own heap allocation, so the size of the per-node record is multiplied by the tens of millions of nodes a large document holds. Two levers recur across the refinements below, and the measured figures throughout this document are live heap memory (the sum of live allocations):

  • Shrink the record — a smaller struct uses less memory on every node or element it applies to. (General-purpose allocators round each request up to a granularity, so a byte reduction shows up as a memory saving in steps; the measured deltas capture the real effect rather than the raw byte count.)
  • Remove the allocation — a list that is empty, or holds a single element, need not own a separate heap buffer at all; eliminating it saves the buffer plus the cost of allocating, freeing and GC- tracing it.

4BOXED — box the Element variantdce407d2

Problem. E4XNodeKind is sized for its largest variant, Element, which holds three Vecs (attributes, children, namespaces). Every node therefore carried that three-Vec footprint inline regardless of kind — including the leaf Text/CData/Comment/PI/ Attribute nodes, which only need a single AvmString and which typically vastly outnumber elements in data-oriented XML (measured leaf fraction ≈ 49%).

Change. Move the Element payload into a heap-allocated E4XElementData, so the variant becomes a single pointer: Element(Box<E4XElementData>). Every non-element node then shrinks by the size of the three Vecs (on wasm32 the node drops from ~68 to ~36 bytes); element nodes pay one extra allocation and one indirection to reach their lists. Box<T: Collect> is traced by gc-arena with no extra GC header. ~70 call sites across 5 files, bodies kept identical by matching Element(elem) and using elem.field.

Measured (250k workload): total live memory 1425.6 → 1222.4 MB (−203 MB). The ~10.9M leaf nodes each drop from ~68 to ~36 bytes.

Reading the numbers WASM linear memory has no memory.shrink, so a footprint win shows up as higher free headroom, not a lower total memory size. Measure live allocations, not total reserved memory.

5INTERN — intern payload strings on parse4b83812f

Problem. Element and attribute local names already went through the AvmStringInterner, but the remaining E4X payload strings did not: text/CData/comment text, processing-instruction targets and values, attribute values, and namespace URIs/prefixes. In data-oriented XML these repeat heavily (the same status codes, flags and column values on every row), so each duplicate spawned its own AvmStringRepr allocation.

Change. Route those payloads through the interner on parse. Value-like payloads pass through a 64-byte length cap so the intern table stays tight on free-text-heavy XML, while name-like payloads (PI targets, namespace URI/prefix) are always interned since their cardinality is bounded per document. Many duplicate AvmStringRepr allocations collapse onto shared interner entries. No effect on the public API or on string lifetimes — the interner holds weak references and stale entries are pruned automatically at GC trace.

Measured (250k workload) A far bigger win than its diff size suggests — second only to BOXED: total live memory 1222.4 → 1053.6 MB (−169 MB). Duplicate string allocations collapse onto shared interner entries; the smallest string allocations alone drop from 4.38M to 1.28M live.
Why a length cap Interning is a win only when strings recur. Short value-like strings (codes, flags) recur constantly; long free text is usually unique, so interning it would only bloat the table. The 64-byte cap keeps the table to the strings that actually dedupe.

6RARE-FIELDS — box the node's rare fields53dfa85a

Problem. Two node-level fields — the node's own namespace and its notification watcher — are unset on the overwhelming majority of nodes (no namespace, no E4X change watcher) yet cost ~12 B of inline storage on every node.

Change. Move both into a side-allocated Gc<E4XRareData> referenced from a single Lock<Option<Gc<…>>> slot, allocated lazily the first time either field is set. Nodes that never use either now pay one pointer instead of two inline option values, shrinking the common E4XNodeData record.

Measured (250k workload): total live memory 1053.6 → 971.3 MB (−82 MB).

7LAZY-NS — lazy namespace listb753d358

Problem. An element's namespaces declaration list was an inline Vec (three pointers). Almost every element in typical data XML — every non-root node — declares no namespaces, yet paid for the inline Vec regardless.

Change. Vec → Option<Box<Vec<E4XNamespace>>>. When empty it is a single niche-optimized pointer (None, allocating nothing), shrinking E4XElementData by 8 bytes (36 → 28 B) and removing the empty-list allocation in the common case. The list is materialized (get_or_insert_with) only on the rare addNamespace path; reads and removals treat None as empty. The intentional Box<Vec> carries an explicit #[allow(clippy::box_collection)]. Measured: −35 MB (892.6 → 857.5 MB).

Note: this is the element's declared namespace list, distinct from the node's own namespace field moved by RARE-FIELDS.

8LAZY-ATTR — lazy attribute list589f4e67

Problem & change. The same lazy-boxing applied to an element's attributes: Vec → Option<Box<Vec<E4XNode>>>. Elements with no attributes (common in data XML) now store a single niche pointer instead of an inline empty Vec, shrinking E4XElementData by another 8 bytes (28 → 20 B).

Reads go through a new E4XElementData::attributes() accessor that returns a slice (empty when None); the shared remove_matching_nodes helper gains an E4XNodeContainer impl for the boxed-option type; the list is materialized only on the mutating add path (setAttribute). Measured: −46 MB (857.5 → 811.1 MB).

9CHILDREN-ENUM — single-child enumb30a3963

Problem. The single-child element (e.g. <col>text</col>) is the dominant shape in data-heavy XML, yet a plain Vec allocated a separate heap buffer just to hold that one child. An intermediate step (54a2fb0a) first replaced the Vec with SmallVec<[E4XNode; 1]> to inline the single child (mirroring avmplus's SINGLECHILDBIT), removing those one-element child-buffer allocations — on its own worth −79 MB (971.3 → 892.6 MB) by eliminating ~5.3M separate child buffers. But a SmallVec<[_; 1]> is three words wide, so it did not shrink the element record itself.

Change. Replace the SmallVec with a purpose-built E4XChildren enum — Empty | One(E4XNode) | Many(Box<Vec>) — which is a pointer plus a discriminant (two words). It preserves the no-allocation single-child case while shrinking E4XElementData to 16 B (20 → 16 B). Deref<Target = [E4XNode]>, IntoIterator and FromIterator provide the whole read/iteration API, so call sites are unchanged; mutation goes through inherent push/insert/remove/retain/clear that maintain the Empty/One/Many invariant (collapsing back on removal). A compile-time assertion guards the resulting struct size. Measured: −37 MB (811.1 → 774.6 MB).

11wasm64 & the safe floor

wasm64. With 64-bit pointers the records are wider, so the absolute byte sizes differ (e.g. the boxed leaf node is ~56 B rather than ~36 B), but the same structural wins apply — and the relative pressure from the node tree is, if anything, higher.

The safe floor. After these six refinements the remaining large target is the per-node E4XNodeData record itself, paid by tens of millions of nodes. Shrinking it further would require, in tandem, removing the RefCell borrow flag from kind and merging local_name with the rare-field pointer into one tagged slot (the avmplus m_nameOrAux idea) — either change alone is too small to lower the record's actual allocation, and done together they force unsafe pointer-tagging and nested GC write-barriers, i.e. a GC-soundness risk. This branch deliberately stops at the safe floor: every refinement here is representation-only, with no unsafe and no correctness risk.

Time vs. memory Parse time is essentially unchanged across all six refinements — it is dominated by the number of Gc::new calls, GC tracing and interning, not by per-node bytes. Reducing parse time would require reducing the node count, a different axis from this branch's footprint work.

Key abstractions introduced

  • E4XElementData — the boxed element payload (attributes, children, namespaces) behind E4XNodeKind::Element(Box<…>).
  • E4XRareData — side record for the node's rarely-set namespace and notification, reached through one lazy Lock<Option<Gc>> slot.
  • E4XChildren — the Empty/One/Many child container with Deref<[E4XNode]> + IntoIterator + FromIterator, so read sites are untouched.
  • E4XNodeContainer — a small private trait that lets remove_matching_nodes work uniformly over Vec, SmallVec and Option<Box<Vec>> (abstracting the retain closure signature difference).
  • E4XElementData::attributes() — slice accessor returning &[] when the lazy list is None.
  • Target-conditional const _ size assertions on E4XChildren / E4XElementData guard the byte budget at compile time.
