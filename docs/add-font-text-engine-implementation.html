1Overview

Ruffle shipped flash.text.engine (FTE) as a shell: the constant classes existed, but TextBlock.createTextLine was a stub that faked a single line, so anything built on FTE — the whole flashx.textLayout (Text Layout Framework) stack that Spark RichText, Label, TextInput and TextArea compose their text with — rendered nothing usable.

This branch turns FTE into a working text-composition engine: real line breaking, real line metrics, a real line chain, caret hit-testing and paragraph justification — enough that the Spark text controls a Flex enterprise application depends on compose, measure, wrap and edit correctly. It is built on the native TextBlock object: upstream refactored TextBlock's storage from AS3 slots to a native Rust TextBlockObject (allocator + native getters/setters), and the composition logic here is grafted directly onto that native model rather than onto AS3 slots.

The headline Spark RichText / Label / TextInput / TextArea now compose, wrap, measure, justify and edit real text, with a working caret and word selection — the FTE surface a typical Flex business application exercises is functional. The gaps that remain (§9) are advanced typography and specialized layout, not the everyday composition path.

What upstream provided, and what this branch adds

Upstream Ruffle shipped the FTE type system — all 32 classes, the eighteen constant/enum classes, the formatting and justifier data holders, and (recently) native TextBlock storage — but no composition: TextBlock.createTextLine was a stub that faked a single line, and TextLine's metrics and hit-testing were stub getters (there was no native text_line.rs module at all). The package was type-complete but inert. Everything this branch contributes is the composition engine — ~1,000 lines concentrated in TextBlock and TextLine — that turns that inert type system into working text. It does not touch the enum classes, ElementFormat, FontDescription, FontMetrics, the justifiers, TabStop or the content-element types; those were already present.

2The composition pipeline

TextBlock.createTextLine(previousLine, width) and recreateTextLine are native (text_block.rs::break_text_line). Rather than reimplement shaping and wrapping, break_text_line reuses Ruffle's existing text layout engine — the same one that lays out classic TextField / htmlText:

  1. Flatten. collect_spans walks the block's content-element tree into one WString plus a list of format runs. A GroupElement recurses over its children; a GraphicElement contributes a single U+FDEF placeholder character, as in Flash Player.
  2. Lay out the remainder. The text after previousLine is laid out at the requested width via lower_from_text_spans (word-wrap on).
  3. Take the first break. The break point for the new line is the start of the second laid-out line (lines[1].start()); everything up to it — including trailing whitespace and the line terminator — is consumed by the new TextLine.
  4. Back it with a field. Each TextLine is backed by an EditText "fallback" holding exactly that one line's text and formats; the fallback performs the actual glyph layout and rendering.

The block's textLineCreationResult reports the outcome: success, complete (all text consumed), insufficientWidth (not even one atom fits and fitSomething is false), or emergency (a word longer than the width had to be broken mid-word).

Cost Laying out the whole remainder to take just the first break is O(N²) in the block's text length. That is fine for the FTE workloads a Flex app produces (labels, form fields, short paragraphs); very large blocks are a known optimization TODO.

3Metrics & the baseline origin

TextLine.ascent, descent, textWidth and textHeight are real, extracted from the backing field's layout into LineMetrics { ascent, descent, text_width }. The subtlety is the coordinate origin. A TextLine's origin is the start of its baseline — text extends to the right and mostly upward — whereas the backing EditText's origin is its top-left corner, inset by the gutter. So both render_self and self_bounds translate the fallback by 

fallback_offset = (-gutter, -(gutter + ascent))

which drops the fallback so its baseline lands exactly on the line origin, like Flash Player. This single offset is the linchpin: rendering, bounds, and every hit-test (§6) are all expressed relative to it, so they land on the same pixels.

4The line chain & native TextBlock

Upstream nativized TextBlock into a TextBlockObject. The composed lines live in that native object: first_line and last_line are native fields, and each TextLine carries _nextLine / _previousLine / _textBlockBeginIndex / _rawTextLength slots. firstLine, lastLine, firstInvalidLine and textLineCreationResult read this chain.

  • createTextLine(null, w) starts a fresh chain (the new line becomes firstLine).
  • createTextLine(prev, w) continues from where prev ended (prev.textBlockBeginIndex + prev.rawTextLength), linking the new line after it.
  • recreateTextLine(line, …) reuses a recycled TextLine object in place instead of allocating a new one — the Text Layout Framework pools lines this way.
  • releaseLines(first, last) detaches an inclusive range, relinks the surrounding chain, and updates the block's native first_line/last_line.

5The validity state machine

Every TextLine has a validity: VALID, POSSIBLY_INVALID, INVALID, or STATIC. Ruffle enforces the same restricted transitions as Flash Player — an illegal one raises ArgumentError #2008 (pinned down by the textline_validity regression test, which this branch takes off the known-failure list). Two flows drive the machine:

  • Content change. Assigning TextBlock.content or bidiLevel walks the chain and flips VALID/POSSIBLY_INVALID lines to INVALID (invalidate_all_lines) — the standard "these lines must be re-composed" trigger.
  • Release. STATIC is the state the Text Layout Framework's factory (StringTextLineFactory, behind Spark RichText/TextArea) puts a line in before releasing it. releaseLines detaches the range, relinks the chain, updates the native endpoints, and invalidates the lines that followed the range — but never a STATIC line.
The STATIC trap With a default SpaceJustifier (which the TextBlock constructor now installs), the Text Layout Framework takes its justified path: it marks each factory line STATIC, then calls releaseLines. A naive releaseLines that invalidates the line hits STATIC → INVALID → #2008 uncaught in enterFrame → the LayoutManager freezes and every Spark component stops laying out. Skipping invalidation for STATIC lines is what lets Spark text render at all.

6Hit-testing — caret & selection

For editable TLF text (TextInput/TextArea), the SDK's SelectionManager places and moves the caret by calling TextLine.getAtomIndexAtPoint, getAtomBounds, getAtomIndexAtCharIndex and getAtomWordBoundaryOnLeft. All are native, and all the care is in the coordinate spaces — kept exactly inverse to fallback_offset (§3) so that where the caret is placed and where it is drawn agree:

  • getAtomIndexAtPoint receives the point in stage (global) coordinates → maps to line-local via global_to_local (origin on the baseline) → into the fallback's gutter-less layout space by adding (gutter, gutter + ascent) → asks the fallback char_index_at_point.
  • getAtomBounds is the reverse: the fallback's char_bounds (layout space) translated up by the ascent into line-local space.
  • getAtomIndexAtCharIndex maps an absolute TextBlock char index to a line-relative atom by subtracting textBlockBeginIndex.
Two edge cases that froze real apps (a) The trailing paragraph terminator is counted in rawTextLength but has no glyph; getAtomBounds for it returns a zero-width box at textWidth, matching FP — otherwise the caret jumped to a garbage coordinate far to the right. (b) getAtomIndexAtCharIndex must subtract textBlockBeginIndex; when it didn't, Spark Label's ellipsis truncation fed a stray -1 into #2006 and froze the whole LayoutManager in enterFrame.

7Justification

A paragraph is justified when its block carries a SpaceJustifier whose lineJustification is "all" (justify every line) or "allButLast"/"allButMandatoryBreak" (justify all but the final line of the paragraph). break_text_line reads that flag and, for a line that should stretch, switches the backing field to Justify alignment and forces it to spread to the requested width even though the fallback holds only that one — otherwise "final" — line, via an ALWAYS_JUSTIFY override. Basic width-justification is therefore correct; the finer spacing envelope (SpaceJustifier.minimum/optimum/maximumSpacing, letterSpacing) is stored but not yet consumed, so the spread is whatever the core Justify pass yields (§9).

8API coverage

A member-by-member audit of the whole flash.text.engine package against the Adobe AS3 surface counts 228 public members: 165 real, 31 partial, 18 stub, 14 missing. That "real" figure is optimistic — roughly a dozen ElementFormat properties are stored and validated but never applied to the glyph, so their real-world effect is nil; counting those as partial, functional coverage is closer to two-thirds. All 32 Adobe classes exist as files, the 18 constant/enum classes are complete, and the core composition path (TextBlock line-breaking, TextLine metrics + hit-testing, ElementFormat's font/size/color/weight/kerning, FontDescription, TextElement, GroupElement) is genuinely implemented; the gaps concentrate in advanced typography and specialized layout.

Coverage ≠ this branch's contribution Most of that "real" count predates this branch: the 66 enum constants and the native property storage of ElementFormat / FontDescription / the data-holder classes were already in upstream. This branch's own contribution is the composition path — the members in the §1 table that went from stub to real, plus the line-breaking engine behind them. Key types

  • TextBlockObject — native TextBlock storage: content, justifier, tab stops, the baseline/rotation/bidi properties, and the first_line/last_line chain endpoints.
  • TextLine (display object) — an interactive display object wrapping an EditText fallback; carries LineMetrics and validity; positioned by fallback_offset.
  • LineMetrics { ascent, descent, text_width } — the measured line, in the line's own baseline-origin space.
  • TextLineValidity (in fte.rs) — the four-state enum + the transition-legality rules that back #2008.
