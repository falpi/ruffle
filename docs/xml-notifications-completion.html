1Motivation

Flash Player's E4X implementation carries an undocumented change-notification protocol (XML.setNotification()) that the Flex framework uses as the backbone of XML data binding: mx.utils.XMLNotifier installs a notification function on every item of an XML data provider, and mx.collections.XMLListAdapter turns each notification into an itemUpdated() → COLLECTION_CHANGE event that refreshes list and grid renderers.

Upstream Ruffle implements only a slice of the protocol (commit d9944b261, “avm2: Trigger XML notifications for attributes changes”): attributeAdded, attributeChanged and nameSet. Every other mutation — assigning element text, adding, replacing or deleting child nodes, deleting attributes, namespace changes — mutates the tree silently.

The practical consequence in a Flex application: a two-way binding that writes item.FIELD = text (an editable grid cell, an “enable the button when the value differs” form) updates the XML but never re-runs the dependent bindings, because the COLLECTION_CHANGE that Flash Player would emit through textSet never fires. Attribute-driven UIs (item.@visible = …) work; element-driven UIs stay stale until something else happens to re-assign renderer data.

Net result This branch completes the protocol: all 11 notification commands that avmplus emits are now implemented — every avmplus emission site, normalize() included — with semantics transcribed from the avmplus sources (XMLObject.cpp, E4XNode.cpp, XMLListObject.cpp) and zero cost on unwatched trees.

2The notification protocol

A notification function is attached per node with xml.setNotification(f) and read back with xml.notification(). On every mutation the player invokes, synchronously, the function of the mutated node and of each of its ancestors: 

function notifier(currentTarget:Object,  // the node whose notification fn is being invoked
                  command:String,        // "textSet", "nodeAdded", "attributeChanged", …
                  target:Object,         // the node the mutation happened on
                  value:Object,          // command-specific payload
                  detail:Object):void    // command-specific detail (usually the old value)

In avmplus the dispatch is XMLObject::issueNotifications: starting from an initial target it walks the parent chain and calls every non-null notification function with a freshly created currentTarget wrapper. Ruffle's equivalent is XmlObject::trigger_notification, which had the walk already — this branch extends the command enum and adds the missing emission sites.

avmplus groups the emission sites behind two helpers, and this branch mirrors that split:

  • nonChildChanges(type, value, detail) — the mutation is a property of the node itself (attributes, name, namespaces, text value). Maps to trigger_notification with target = self.
  • childChanges(type, value, prior) — the mutation is about a child (nodeAdded/nodeChanged/nodeRemoved). Fires only when the value is an XML or XMLList object, and passes the replaced node, if any, as detail. Maps to the new XmlObject::trigger_child_changes helper, which replicates both rules.

4Architecture of textSet

The single most consequential design decision, taken directly from avmplus (ElementE4XNode::_replace): textSet is emitted inside the [[Replace]] primitive itself — E4XNode::replace, text branch — not by its callers. The notification originates from the newly created text node: target = the text node, value = the new string, detail = the prior node's value (when the replaced slot held a value-kind node).

Because every path that turns a string into element content funnels through [[Replace]], one emission site covers them all: XML primitive assignment (x.child = "s"), XMLList numeric put (list[0] = "s"), XML.replace() and setChildren() with a string, and string children in [[Insert]].

Fidelity note Assigning the empty string emits nothing — in Flash Player too. avmplus only calls [[Replace]] (and therefore textSet) when the coerced string is non-empty; clearing a field silently deletes the element's children. Consumers that must react to a cleared value need an attribute or a collection-level refresh, on both runtimes.

5Caller-side commands: childChanges

Structural commands are emitted by the operations, mirroring avmplus call sites one by one. The helper enforcing the avmplus rules is: 

// xml_object.rs — equivalent of avmplus XMLObject::childChanges
pub fn trigger_child_changes(self, activation, command, value: Value, prior: Option<E4XNode>) {
    if !self.node().notify_needed() { return; }                 // fast path (§6)
    if value is neither XmlObject nor XmlListObject { return; } // avmplus isXML/isXMLList gate
    let detail = prior → XmlObject wrapper, else undefined;
    self.trigger_notification(activation, command, value, detail);
}

6The notify_needed fast path

avmplus guards every emission with XMLObject::notifyNeeded — a walk up the parent chain checking for a non-null notification function — before allocating wrapper objects and argument lists. The branch replicates it as E4XNode::notify_needed().

On unwatched trees (the overwhelmingly common case: parsers, data pipelines, read-mostly providers) every new emission site reduces to that pointer walk, or to nothing at all where the check was already needed for other reasons. No wrapper objects, no argument marshalling, no interned-string lookups are performed unless a notification function is actually reachable.

7Re-entrancy & borrow discipline

A notification is a synchronous call into arbitrary AS3 in the middle of a mutation. In Flex that callback chain is XMLNotifier → XMLListAdapter → itemUpdated → COLLECTION_CHANGE → framework handlers that routinely read the same XML tree.

Ruffle's E4X node internals live in RefLock cells: invoking AS3 while a kind_mut() / children_mut() borrow is outstanding turns the first framework read-back into a RefCell double-borrow panic. The rule adopted throughout the branch:

Rule A notification may only be emitted when no borrow of any node's interior state is live and the tree is in a consistent state (in particular, never while a placeholder dummy node from the two-phase replace idiom is still reachable).

Concretely, three pre-existing spots were restructured because they would have panicked once their inner [[Replace]] started emitting textSet:

  • XmlObject::set_property_local, step 13 — the target child is now extracted in a closed scope before remove_all_children/replace run, instead of holding the parent's kind_mut across the call;
  • XmlListObject::delete_property_local — the numeric removal happens in its own scope, the notification after it; the recursive non-numeric path collects the child nodes first and iterates without holding the list borrow;
  • XmlListObject::set_property_local, step 3.b — the delegating [[Put]] no longer runs with the list's RefMut alive (the borrow is now scoped to the child lookup statement).

Emission points are placed after the mutation completes (avmplus does the same), so a callback that re-enters E4X — even one that mutates the same node again, recursively — observes a consistent tree.

Two details worth keeping in mind when debugging bindings on top of this chain:

  • XMLListAdapter.xmlNotification calls itemUpdated unconditionally — the command-specific switch only refines the property name and old/new values placed in the PropertyChangeEvent. Any notification reaching the adapter produces an UPDATE.
  • Attribute writes worked before this branch; that asymmetry is why attribute-driven screens (tree checkboxes toggling @visible) behaved while element-text screens did not — a useful signature for recognizing the class of bug this branch removes.

9Known limitations

  • Ordering deviations on multi-event operations. When a named replace() or a property set collapses duplicate children and replaces content, the nodeRemoved events may be observed after the textSet/nodeChanged rather than before — a consequence of only emitting on a consistent tree (§7). The event set matches avmplus; the interleaving may not, byte for byte.
  • XMLList empty-attribute creation. avmplus emits an early attributeAdded (no detail) when list[i] materializes an empty attribute, then an attributeChanged when the value lands. Ruffle's flow adds the attribute and its value in one step, emitting a single attributeAdded carrying the final value — same net observable state, one event instead of two.
