Text Input Event Dispatch

Why Flex Spark and Text Layout Framework text fields render but can't be typed into, and the small piece of plumbing that fixes it: deliver TextEvent.TEXT_INPUT to whatever object holds focus, not only to native text fields.

Audience
Maintainers, reviewers, anyone chasing keyboard input that never reaches a TLF-backed or otherwise custom text component
Scope
Delivery of character input (TextEvent.TEXT_INPUT) to focused AVM2 interactive objects other than a native text field. The native EditText input path, raw KeyboardEvent dispatch, and IME composition are untouched.

A Flex Spark TextInput, TextArea, or editable ComboBox renders its text in Ruffle and can be focused, but silently ignores the keyboard: nothing you type appears. These controls are not native text fields — they are backed by the Text Layout Framework (TLF), whose EditManager runs on an ordinary Sprite and expects to receive typed characters as a TextEvent.TEXT_INPUT. Ruffle delivered that event only to native EditText objects, so the character never reached TLF and the field could not be edited. This document explains how Flash Player routes keyboard input, the single-channel gap in Ruffle, and the additive fix that closes it without disturbing the well-tested native text-field path.

1The symptom

In a Spark component showcase run under Ruffle, every non-text widget behaves: buttons, checkboxes, sliders, lists, dropdowns and data grids render and respond. The text-entry controls are the exception. TextInput, TextArea and the editable ComboBox display their initial content correctly — proof that text composition and rendering work — but pressing keys does nothing. The caret may appear, the field takes focus, yet no character is inserted, nothing is deleted, and the value never changes.

There is no error, no stub warning, and no visual artifact other than an unresponsive field. The initial text is visible because it was composed through the Text Layout Framework onto flash.text.engine lines, which already work; only the interactive path is dead.

2How Flash Player delivers keyboard input

2.1 Two independent channels

When an interactive object holds focus and the user presses a key, Flash Player delivers the keystroke through two separate event channels, both targeted at the focused object regardless of its type:

  • KeyboardEvent (keyDown / keyUp) — carries the raw key code and modifiers. Used for navigation and command keys: arrows, backspace, delete, Home/End, and clipboard shortcuts.
  • TextEvent of type TEXT_INPUT — carries the actual character(s) produced by the keystroke (respecting layout, shift, dead keys and IME). This is how the content of a keystroke is delivered. It bubbles and is cancelable.

A native TextField is simply the object that, by default, listens to its own TEXT_INPUT and inserts the character. But the event itself is dispatched to whatever InteractiveObject has focus — a Sprite with focus receives TEXT_INPUT exactly the same way. That is the mechanism any non-TextField text component relies on.

2.2 How TLF-backed components consume it

The Flex 4 Spark text controls (spark.components.TextInput, TextArea, and the text entry of an editable ComboBox) are all built on spark.components.RichEditableText, which is a Sprite-derived UIComponent — not a TextField. For editing it installs a Text Layout Framework flashx.textLayout.edit.EditManager on its TextFlow. The EditManager (through the container manager) listens for TextEvent.TEXT_INPUT on the container Sprite; on each event it mutates the TextFlow model, then recomposes it through flash.text.engine (TextBlock.createTextLine) into the visible lines.

Key point TLF never uses a native TextField for editing. The typed character reaches it only as a TextEvent.TEXT_INPUT dispatched to the focused Sprite. If that event is not delivered, the field is inert no matter how well composition and rendering work.

3The gap in Ruffle

3.1 Text input routed only to native text fields

Ruffle turns platform key events into three internal input events — TextInput (a character), TextControl (an editing command such as copy/paste/select-all), and Ime (composition) — and, in player.rs, delivered all three to the focused object only if that object was a native text field: 

// Before — player.rs
if !key_press_handled
    && let Some(text) = context.focus_tracker.get_as_edit_text()
{
    if let InputEvent::TextInput { codepoint } = &event {
        text.text_input(codepoint.to_string(), context);
    }
    if let InputEvent::TextControl { code } = &event {
        text.text_control_input(*code, context);
    }
    if let InputEvent::Ime(ime) = &event {
        text.ime(ime.clone(), context);
    }
}

FocusTracker::get_as_edit_text() returns Some only when the focused display object is an EditText. When focus was on any other interactive object — a Sprite hosting a TLF EditManager, or any custom text component — the whole block was skipped and the character was silently discarded. It was never dispatched anywhere.

3.2 What already reached the focused object

Raw KeyboardEvents were not restricted this way: Ruffle already dispatches keyDown/keyUp to whatever object the focus tracker points at (falling back to the stage), for AVM2 targets. So the focused TLF Sprite did receive arrow keys and backspace as KeyboardEvents — but with no TEXT_INPUT ever arriving, there was no character to insert in the first place. The asymmetry is exactly the bug: navigation could reach the component, content could not.

4The fix

4.1 Dispatch textInput to the focused object

The block becomes an if/else if: the native EditText path stays first and unchanged; when the focused object is not an EditText, and the input is a character, Ruffle now dispatches a flash.events.TextEvent of type textInput (bubbling and cancelable, matching Flash Player) to the focused AVM2 object: 

// After — player.rs (new branch only)
} else if let InputEvent::TextInput { codepoint } = &event
    && let Some(focus) = context.focus_tracker.get()
{
    let target = focus.as_displayobject();
    if target.movie().is_action_script_3()
        && let Some(target_object) = target.object2()
    {
        let mut activation = Avm2Activation::from_nothing(context);
        let text = AvmString::new_utf8(activation.gc(), codepoint.to_string());
        let text_evt = Avm2EventObject::text_event(
            &mut activation, "textInput", text, true, true);
        Avm2::dispatch_event(activation.context, text_evt, target_object.into());
    }
}

The event object is built with the same Avm2EventObject::text_event helper that the native EditText already uses to fire its own textInput, so the two paths construct identical events. Dispatch is gated to AVM2 targets (movie().is_action_script_3()), consistent with the neighbouring KeyboardEvent code. A TLF EditManager listening on the focused Sprite now receives the character and inserts it.

4.2 Leaving the native text-field path intact

Because an EditText is always caught by the first branch (get_as_edit_text()), it never reaches the new code — the native insertion, its own textInput dispatch, restrict filtering, IME and text-control handling are byte-for-byte the same as before. The new branch runs only for focused objects that are not text fields, which previously did nothing at all. The change is strictly additive: it turns a silent drop into a Flash-correct dispatch, and cannot alter any path that already worked.

Why additive, not a refactor Flash Player's most literal model is "always dispatch TEXT_INPUT to the focused object; if it is a text field and the event is not canceled, insert". Restructuring the heavily-tested EditText path to that shape would risk regressions in existing text-field behavior for no functional gain here. Keeping the native path untouched and adding a sibling branch delivers the same observable result with none of that risk.

5Fidelity and behavior notes

  • The event matches Flash Player. Type textInput, bubbles = true, cancelable = true, text = the typed character. It is dispatched to the focused object and bubbles through its ancestors, so both TLF's listener and any application handler see it.
  • Any focused interactive object receives it, not just text components. This is Flash-correct: in Flash Player a focused button or plain sprite also receives TEXT_INPUT (harmlessly, with no default action). Restricting delivery to "looks like a text field" would be both wrong and fragile.
  • KeyboardEvents are unchanged. They already reached focused objects; navigation and command keys (arrows, backspace, clipboard shortcuts) continue to flow through that channel, which is also how TLF handles them.
  • IME composition to non-text-field focus is not yet routed. Committed IME text and pre-edit composition still take the native EditText path only; wiring them to the focused object is a natural follow-up on the same block. Latin/ASCII typing — the reported gap — is fully covered.
  • TextControl (editing commands) stays native-only by design. For a TLF component these arrive as KeyboardEvents that its own EditManager interprets, so no synthetic text-control event is needed or wanted.

6Impact and coverage

The immediate beneficiaries are the Flex 4 Spark text controls, all of which route editing through a TLF EditManager on a Sprite:

  • spark.components.TextInput and spark.components.TextArea;
  • spark.components.RichEditableText directly;
  • the editable text entry of spark.components.ComboBox.

Beyond Flex, any AVM2 content that puts a non-TextField interactive object in focus and relies on TextEvent.TEXT_INPUT — custom text editors, in-house UI toolkits, games with typed input on a sprite — now receives typed characters as Flash Player delivers them. Content that focuses native TextFields is entirely unaffected.
