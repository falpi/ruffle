Flash Player renders a 1-pixel line drawn with graphics.lineStyle(1, color) + moveTo/lineTo as a crisp, single-pixel-wide run of solid color — even with pixelHinting=false, which is the default. Ruffle rendered the same line smeared across two pixel rows or columns at roughly 50% alpha. This document explains where that difference comes from, why it appears and disappears depending on where a container happens to sit, why the obvious fixes don't survive contact with real Flex/Spark content, and how the three fixes on this branch close the gap for every ActionScript-drawn case found so far.

1The symptom

1.1 Where it appears

Blurry 1px lines were reported and reproduced across superficially unrelated pieces of Flex/Spark UI. They all reduce to the same three underlying mechanisms, which is why they are fixed together on this branch:

  • mx:DataGrid / mx:AdvancedDataGrid separators. The Flex SDK draws horizontal grid lines with a stroke (lineStyle(1) + lineTo) and vertical ones with a 1px drawRect fill, into the same linesBody graphics, inside a lines sprite that the SDK marks cacheAsBitmap = true. Enabling horizontalGridLines made every separator blurry, including the fill-based vertical ones that were crisp without it (§5 explains why).
  • Spark <s:Line> with SolidColorStroke weight="1". Both standalone separators and the column/header/row separators of s:DataGrid, which are <s:Line> GraphicElements drawn into a shared canvas sprite at their own layout offsets.
  • 1px <s:Rect> stroke borders in Spark skins (e.g. a ComboBox border), i.e. rectangle outlines mixing horizontal and vertical segments in a single path.
  • Text carets, underlines, and device text field borders, which do not go through the drawing API at all but through the renderer's draw_line primitive (§6).

1.2 Why it comes and goes

The most confusing property of the bug: the same component could render crisp or blurry depending on where it sat, and dragging a window sometimes toggled it. A stroke is crisp when its geometry happens to land on the pixel grid after the full chain of transforms; a container positioned at x = 100.0 produces a different sub-pixel phase than the same container at x = 100.5 — and Flex/Spark layouts produce fractional positions routinely (percent-width resolvers, centered popups, measured text sizes). Some components were crisp by pure accident of placement, others blurry, and the original reports ("AdvancedDataGrid body lines are blurry only with grouped columns") were downstream of coordinate coincidences, not of the features they seemed to correlate with.

2Rasterization background

2.1 Strokes are centered on the path

Ruffle stores coordinates in twips (1 px = 20 twips) and tessellates ActionScript drawing paths with lyon. Lyon's stroke tessellator centers stroke geometry on the path: a 1px-wide vertical stroke along x = X becomes a quad spanning [X − 0.5, X + 0.5]. When X is an integer — which is what application code almost always writes — both quad edges sit exactly mid-pixel, and the rasterizer (with or without MSAA) covers two pixel columns at ~50% each. The result is a soft, ~2px-looking gray line instead of a solid 1px one.

2.2 The two sources of misalignment

Crispness is a property of the stroke center in screen space: center = world_transform × path_coordinate. Both factors contribute fractions, and any fix that only looks at one of them is structurally incomplete:

  • The world transform. The host sprite's accumulated translation is fractional whenever a layout places a container at N.5 (Spark does this constantly). A path drawn at a perfectly integer local coordinate then lands mid-pixel on screen.
  • The path coordinates themselves. Spark GraphicElements share their parent Group's canvas sprite: each element draws at its own layout position via moveTo(measuredX + drawX, …). All the column separators of an s:DataGrid therefore live in one Drawing, each at a different x — with different sub-pixel phases whenever column widths are fractional. No single adjustment of the world matrix can align them all at once.

2.3 What Flash Player does

Flash Player's rasterizer snaps 1px orthogonal strokes onto whole pixel rows/columns regardless of the pixelHinting flag — the flag widens the set of snapped cases, but the hairline/1px orthogonal case is always crisp. The same holds for its native text caret and text field borders. Ruffle's tessellate- then-transform pipeline has no equivalent step, which is the gap this branch fills — for the ActionScript drawing path only, since SWF-embedded shapes come pre-authored at whatever coordinates the tool chose, are covered by golden tests, and were not part of any report.

3Lessons from the first iteration

An earlier iteration of this branch attacked the problem in path space: the tessellator pre-shifted qualifying 1px orthogonal stroke paths by +0.5px perpendicular (so lyon emitted (X, X+1) quads), and Drawing::render floor-snapped the world translation for drawings made exclusively of such strokes. It fixed the original grids but kept breaking on new content, and each failure exposed a structural limit rather than a bug:

  • Path-space shifts are defeated by the transform. The +0.5 pre-shift is correct only if the world translation is integer. The compensating floor-snap applied per-Drawing, all-or- nothing — so a drawing mixing fills and strokes (the DataGrid body!) could never be gated in without dragging its fills along.
  • Rectangle outlines can't take a single perpendicular shift. A drawRect stroke mixes horizontal and vertical segments; the tessellator-side fix had to bail on them entirely, which is why 1px <s:Rect> skin borders stayed blurry.
  • Shared canvases carry multiple phases. Separators drawn by different GraphicElements into one Drawing sit at different sub-pixel phases; one translation cannot align them (§2.2).
  • Touching the tessellator touches everything. The pre-shift applied to SWF-embedded shapes too, which is where most of the golden-test churn in CI came from.

The redesign keeps exactly one idea from that iteration — the cacheAsBitmap bounds snap of §5, including its hard-earned gating — and replaces the rest with a mechanism that works per run of paths, in screen space, with the final world matrix in hand.

4Fix 1 — screen-space per-run stroke snapping

All ActionScript-drawn geometry — AVM1 and AVM2 graphics, Shape/Sprite/ MovieClip, and Spark's shared canvases — funnels through a single render entry point: Drawing::render in core/src/drawing.rs. That is where the fix lives. The tessellator, the shaders, and the per-backend shape pipelines are untouched.

4.1 Render units and runs

Previously a Drawing registered one backend shape containing all of its paths and rendered it with the world transform. Now Drawing::render partitions the finalized path list (the same list the single-shape path used — committed paths, then the still-open fill/lines with their auto-close segments) into runs of consecutive paths, and registers one shape per run:

  • Paths that qualify for snapping (§4.2) and are mutually compatible accumulate into a snappable run, carrying the parameters needed to compute the snap at render time.
  • Everything else — fills, wide or diagonal strokes, gradient strokes, phase-incompatible strokes — accumulates into plain runs that render with the untouched transform, exactly as before.

Because runs are strictly consecutive slices rendered in the original order, painter's-algorithm compositing is preserved bit-for-bit: overlapping fills and strokes still draw over each other exactly as they would inside a single shape. The partition is cached (render_units: OnceCell<Vec<RenderUnit>>) and invalidated by the same mark_dirty that invalidates the legacy single handle; register_or_replace keeps its old behavior for its other consumer (glyph drawings in font.rs). 

pub fn render(&self, context: &mut RenderContext) {
    if self.is_empty {
        return;
    }
    let units = self
        .render_units
        .get_or_init(|| self.build_render_units(context.renderer));

    let base_transform = context.transform_stack.transform();
    for unit in units {
        let mut transform = base_transform.clone();
        if let Some(snap) = unit.snap {
            snap_hairline_run(&mut transform.matrix, snap);
        }
        context
            .commands
            .render_shape(unit.handle.clone(), transform);
    }
}

4.2 What qualifies for snapping

hairline_snap_profile(style, commands) classifies one stroke path. It returns Some(SnapParams) when every condition holds, None otherwise — and a None path renders exactly as on mainline:

  • solid-color stroke (FillStyle::Color; gradient/bitmap strokes are excluded);
  • width ≤ 1px (≤ 20 twips — this includes the SWF hairline, width 0, which rasterizes 1px wide);
  • only MoveTo/LineTo commands, every segment purely horizontal or purely vertical (curves and diagonals disqualify — there is no pixel-aligned target for them, and Flash anti-aliases them too);
  • all vertical segments share the same sub-pixel phase of their x coordinate, and all horizontal segments share the same phase of their y coordinate — phase being twips.rem_euclid(20). This is what makes a single translation able to align the whole path at once.

The profile records one sample coordinate per axis: the x of a vertical segment (if any) and the y of a horizontal segment (if any). A rectangle outline therefore qualifies on both axes — the case the previous iteration had to give up on. Two consecutive qualifying paths merge into the same run only if their phases are compatible per axis: 

/// Everything needed to compute, at render time, the screen-space
/// translation that puts a run of 1px orthogonal strokes on the grid.
struct SnapParams {
    sample_x: Option<Twips>, // local x of one vertical segment
    sample_y: Option<Twips>, // local y of one horizontal segment
}

impl SnapParams {
    fn try_merge(&self, other: &SnapParams) -> Option<SnapParams> {
        fn axis(a: Option<Twips>, b: Option<Twips>) -> Result<Option<Twips>, ()> {
            match (a, b) {
                (Some(a), Some(b)) if pixel_phase(a) != pixel_phase(b) => Err(()),
                _ => Ok(a.or(b)),
            }
        }
        Some(SnapParams {
            sample_x: axis(self.sample_x, other.sample_x).ok()?,
            sample_y: axis(self.sample_y, other.sample_y).ok()?,
        })
    }
}

Strokes with different phases simply fall into different runs and are snapped independently — this is how a shared Spark canvas with separators at arbitrary fractional columns comes out uniformly crisp, something no per-Drawing scheme could achieve.

4.3 The snap itself

At render time, per snappable run and per axis, the screen-space stroke center is computed from the sample coordinate and the actual matrix coefficients, then moved onto the half-pixel of the pixel that contains it: 

const PX: f64 = 20.0; // twips per pixel
if let Some(sx) = snap.sample_x {
    let center = matrix.a as f64 * sx.get() as f64 + matrix.tx.get() as f64;
    let snapped = (center / PX).floor() * PX + PX / 2.0;
    matrix.tx += Twips::new((snapped - center).round() as i32);
}
// … same for sample_y with matrix.d / matrix.ty …

floor(center) + 0.5 is majority coverage: the stroke goes to the pixel that already received most of its ink, so it never moves by more than half a pixel and never "jumps" a column as a container slides across fractions. For the ubiquitous integer-coordinate case it selects the pixel to the right/below of the coordinate line, which matches both the previous iteration's validated output and the placement Flex content was designed around. With the center at N + 0.5, lyon's quad edges land exactly on N and N + 1: one full pixel column, stable under plain AA and MSAA alike (Figure 1).

4.4 The rigidity gate

Snapping is only meaningful when the shape reaches the screen unscaled and unrotated, so the adjustment applies only when the matrix is a pure translation. The comparison uses a tolerance, SNAP_EPS = 1e-5, because Spark's percent-based layouts accumulate floating-point drift through matrix concatenation (observed around 1e-7): an exact a == 1.0 check silently disabled the fix for the very content it targeted. The tolerated drift cannot bias the result, because the center is computed with the actual coefficients (matrix.a * sx), not with an assumed scale of 1. Scaled, rotated, skewed, or flipped drawings render exactly as before — zoomed content is anti-aliased in Flash too.

4.5 Properties and costs

  • Degenerate gracefully: a drawing with no qualifying stroke produces a single plain run — one shape, one draw, identical to mainline. Grid drawings with integer coordinates produce 1–3 runs; the worst case (per-column fractional phases) produces one small run per phase.
  • Hit-testing, bounds, and ActionScript-visible state are untouched: only the translation used for the draw command changes, by at most half a pixel.
  • Re-registration cost is unchanged in kind: Flex redraws its graphics per updateDisplayList, which already re-registered the single shape; now it re-registers a handful of smaller ones.
  • Backend-agnostic: the adjustment happens before command recording, so wgpu, webgl and canvas all benefit identically, with no shader changes.

5Fix 2 — cacheAsBitmap bounds snap

The DataGrid repro had a second, independent cause. Drawing::stretch_bounds expands a drawing's bounds by the stroke radius — ±0.5px for a 1px stroke. When such a drawing sits in a subtree rendered through the bitmap cache (Flex sets lines.cacheAsBitmap = true on its grid-lines sprite), render_base derives the offscreen translation from bounds.x_min: a fractional x_min (say −0.5) shifts every vertex of the subtree by half a pixel inside the cached bitmap. This is how enabling stroke-based horizontal grid lines made the fill-based vertical separators blurry too: the fills were pixel-aligned in isolation, and the cache offset dragged them off the grid.

The fix floors bounds.x_min/y_min to whole pixels before computing the offset — but only when the subtree actually contains an ActionScript-drawn 1px orthogonal stroke, the one condition that produces the artificial half-pixel expansion: 

if subtree_contains_drawing_with_hairline_stroke(this) {
    bounds.x_min = Twips::from_pixels(bounds.x_min.to_pixels().floor());
    bounds.y_min = Twips::from_pixels(bounds.y_min.to_pixels().floor());
}

The gate matters as much as the snap. Fractional cache bounds also arise from legitimate placement — bitmaps intentionally positioned at half-pixel coordinates, filtered content whose offscreen texture must preserve its fractional offset — and snapping those visibly shifts the result: an ungated version of this change failed 16 golden tests across cache_as_bitmap and filters. The gating predicate (Drawing::contains_orthogonal_hairline_stroke) is the permissive cousin of §4.2's profile: it tolerates coexisting fills and requires no phase consistency, because any 1px orthogonal stroke stretches the bounds.

Trap — Graphic::drawing_mut() initializes on read The subtree walk needs to inspect each Graphic's dynamic Drawing. The pre-existing accessor, drawing_mut(), is get_or_init-based: merely calling it on a Graphic that never drew installs an empty Drawing, and Graphic::render_self then renders that empty drawing instead of the SWF-embedded shared.shape — the embedded geometry disappears from the screen. An early version of the gate did exactly this and blanked out 18 golden tests. The branch adds a read-only Graphic::drawing() -> Option<Ref<Drawing>> accessor (mirroring the one MovieClip already had) and the rule: tree walkers must never use drawing_mut() for inspection.

6Fix 3 — GL line-primitive emulation

Text carets, text underlines, and device text field borders don't go through the drawing API: core emits them as CommandHandler::draw_line / draw_line_rect commands, already snapped to the pixel grid by EditTextPixelSnapping. Whether they rasterize crisp then depends entirely on how the backend draws a "line".

The wgpu backend had two paths: hardware line primitives (with a +0.5px nudge so the line runs through pixel centers), and — for Dx12 only — an emulation that draws the line as a 1px quad with whole-pixel edges, added because "DirectX does support drawing lines, but it's very inconsistent. With MSAA, lines have 1.4px thickness". The catch: wherever GL is implemented on top of DirectX, the GL backend inherits exactly that inconsistency. On Windows, ANGLE translates GL lines into D3D11 lines — and the web build running in any Chromium-based host (browser or Electron) over WebGL2 is precisely wgpu's Backend::Gl on ANGLE. Result: soft, ~1.4px gray carets and text borders on the platform most users run, while native Vulkan/Metal rendered them fine. 

// render/wgpu/src/surface/commands.rs
let emulate_lines = matches!(descriptors.backend, Backend::Dx12 | Backend::Gl);

The pure-WebGL fallback backend had the same defect (GL LINE_STRIP/LINE_LOOP primitives) and switches to the shared emulation helpers (ruffle_render::lines::emulate_line{,_rect}), which fit a 1px quad between the transformed endpoints — thickness and caps deliberately not transformed — yielding [N, N+1] edges everywhere. Vulkan and Metal keep their hardware-line path, so CI image tests (which run on Vulkan) see no difference.

AAppendix — Design notes & rejected approaches

A.1 Why not snap in the vertex shader?

A per-vertex round() on the snap axis, applied to draws tagged by the tessellator, would handle per-segment phases without any run splitting. It was rejected because it must be implemented and kept in sync across every backend (wgpu WGSL, webgl GLSL, canvas has no shader at all), it needs the device-pixel mapping inside the shader, and the tagging still requires tessellator changes — the exact coupling this design avoids. The CPU-side per-run adjustment achieves the same result for the content that matters, in one place, backend-agnostically.

A.2 Why not always floor the cacheAsBitmap bounds?

Because fractional bounds are usually intentional. Filters and half-pixel-placed bitmaps rely on the offscreen preserving their exact offset; the ungated floor demonstrably broke 16 golden tests. The stroke radius expansion is the one artificial source of fractional bounds, hence the gate.

A.3 Why majority coverage instead of a fixed direction?

The first iteration effectively forced "the pixel to the right/below" via its +0.5 path shift, which is correct for integer coordinates but biased for fractional ones, and its floor-based translation snap produced a one-pixel visual shift in some skins (a header bottom border detaching from the first row). Snapping the center to the containing pixel keeps every stroke within half a pixel of where the application put it and reduces to the validated behavior in the integer case.

A.4 Interaction of the three fixes

They compose without coordination: inside a cached subtree, §5 makes the offscreen offset whole-pixel and §4 then snaps strokes within that offscreen's own grid; §6 is orthogonal, covering primitives that never enter the drawing pipeline. Each is independently revertible.
