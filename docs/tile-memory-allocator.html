Tilemalloc

A size-class allocator with intrusive free lists for long-running, small-allocation-heavy WASM workloads.

1Motivation

Enterprise ActionScript 3 applications that pour large XML documents into data grids are the worst case for a general-purpose allocator. A grid bound to an E4X document materialises hundreds of thousands of tiny, short-lived heap objects per load (E4X nodes, item renderers, binding watchers, event structures). On wasm32-unknown-unknown Ruffle ships dlmalloc, whose free-list traversal and coalescing cost grows with the live set — exactly the wrong cost curve for this access pattern.

Tilemalloc collapses that cost to O(1) push/pop on per-class intrusive free lists, and never coalesces on free. AS3 GC cycles otherwise compound the problem: each cycle sweeps and frees a large population of small objects, and every free pays the coalescing tax. With tilemalloc, tiles freed by an object's destruction stay carved at their size, ready to be popped by the next allocation of the same shape — a construct/destruct loop settles into reuse with no extra memory.grow() past the initial extent fills. It installs as the binary's #[global_allocator]; over-sized or over-aligned requests fall through to the system allocator transparently. There is no AS3 surface.

The headline A 250,000-row XML document that never finishes loading under dlmalloc (aborted after 5 minutes) loads in ~40 seconds with tilemalloc — this changes which documents the player can open at all, not just how fast. The 100k-row case roughly halves (~30 s → ~15 s on a fresh heap). See §11.

2The size-class model

The allocator is configured (in config.rs) as a list of size classes, each a (size_bytes, extent_mb) pair. For every request, pick_class walks the ascending-ordered list once and picks the smallest class whose size_bytes ≥ Layout::size and tile_align ≥ Layout::align; anything that fits no class returns None and takes the system fallback.

  • tile_align is auto-derived, not a config knob: the greatest power-of-two divisor of size_bytes (size_bytes & size_bytes.wrapping_neg(), its lowest set bit). For pow-2 sizes it equals the size; for 24/48/96 it lands on 8/16/32 — enough for the vast majority of Rust types (align ≤ 8).
  • size_bytes ≥ 4 is required: a free tile reuses its first pointer-sized bytes for the intrusive next link (4 B on wasm32), so classes of 1–3 bytes are not representable and the config validator rejects them.

The shipped default covers the 8–256 byte range — where the churn concentrates — at sub-power-of-two granularity:

RangeStepClasses
8 → 64 B88, 16, 24, 32, 40, 48, 56, 64
80 → 256 B1680, 96, 112, 128, 144, 160, 176, 192, 208, 224, 240, 256

That is 20 classes, with 8 MiB reserved per extent — ~160 MiB of pool address space if every class is touched. Anything above 256 B falls back to dlmalloc.

3alloc & dealloc — O(1)

Within a class, alloc is a three-step fast path and dealloc is a single push — no list walk, no coalescing search, no size search, ever.

  1. Free list non-empty → pop the head. This recycles a recently-freed tile, likely still hot in cache.
  2. Else bump range available (bump_ptr < bump_end) → carve one tile off the front and advance bump_ptr += tile_size.
  3. Else → add_extent to install a fresh bump range, then retry step 2.

dealloc pushes the tile back onto the free-list head and returns. Tiles enter the free list exclusively through dealloc; fresh tiles are handed out by the bump pointer.

4Extents & the bump carve

Capacity is added one extent at a time. An extent is a contiguous region of ~extent_mb MiB from the system allocator. Rather than eagerly chaining every tile of a fresh extent onto the free list, each class keeps a bump range [bump_ptr, bump_end) into the current extent and carves tiles lazily as it advances. The invariant extent_total = tile_size × tiles_per_extent is exact, so bump_ptr < bump_end is a sufficient check that a whole tile fits before a carve. Each extent is recorded as ExtentRecord { ptr, total_bytes } for stats and as the anchor trim uses.

Why bump carve (not an eager free-list build) An eager build writes a next pointer into every tile up front — for the 8-byte class with an 8 MiB extent that is 1,048,576 sequential stores at the first allocation, each touching a fresh WASM linear-memory page, paid as a visible stall. The bump carve replaces that with two pointer stores (bump_ptr, bump_end) and amortises each tile's page touch across the subsequent allocs. Empirically this reclaimed ~2–3 s of a ~15 s boot.

5realloc

The default GlobalAlloc::realloc always does alloc(new) + memcpy + dealloc(old). That holds two tiles live at once and pressures the source class's free list — a driver of peak-transient overshoot that can force extra extents under sustained reallocation (think Vec::push growth loops).

Tilemalloc overrides it with an in-place fast path: when the new size still maps to the same size class as the old layout.size(), the existing tile is already big enough, so it returns the same pointer unchanged — zero alloc, zero copy, zero dealloc, and no transient where two tiles are simultaneously alive in the same class. Only a genuine cross-class transition falls back to the standard alloc+copy+dealloc sequence (and is counted — see §7).

6trim — reclaiming empty extents

The steady state is deliberately grow-only: extents are never returned, so reuse is free. But a one-off spike — millions of short-lived objects in one class faster than the GC reclaims them — would otherwise strand its extents forever, and WASM linear memory never shrinks. trim is the escape hatch.

trim_empty_extents runs only when called and is allocation-free (it executes as the global allocator, so it must not re-enter itself). Per class it:

  1. sorts the class's extents by address in place (zero allocation);
  2. sweeps the free list, bucketing each free tile to its owning extent via a binary search (partition_point), counting tiles per extent;
  3. System::deallocs every extent whose tiles are all free (free_count == tiles_per_extent) — never the current bump extent;
  4. rebuilds the free list from the kept buckets plus any orphan tiles.

Two triggers: an automatic last-resort retry inside the fallback path (if a system alloc would OOM, trim runs once and the alloc is retried — trim is alloc-free, so no recursion), and an explicit TileAllocator::trim(), re-exported to JS as tilemallocTrim for a memory-pressure or post-GC hook.

Validated in the field After a 250k-row grid sort produced a transient spike, tilemallocTrim() released ~2 GB. No forced collection is needed first: the spike's objects are gc-arena managed, and gc-arena collects automatically every frame once the synchronous call returns — so by the time trim runs (a few frames later) the spike's extents are already empty.

7Diagnostics

The pool carries nine built-in instruments. They are a permanent part of the allocator — what makes it tunable — with negligible overhead (1–3 ops per alloc/dealloc; the realloc counters touch only the slow path) and ~3–5 KB of state for the default config. The three histograms are gated by the build-time constant config::ENABLE_HISTOGRAMS (default false): when off, LLVM dead-code-eliminates their hot-path updates and the JSON omits them. The other six scalar instruments are always on.

Live vs lifetime. Live counters (waste, requested, histograms) are incremented at alloc and decremented at dealloc using the Layout Rust guarantees is identical at both ends, so a diff of two snapshots reports exactly how the pool's state changed in between — no heuristics. Lifetime counters (alloc, dealloc, extents added/released, all realloc counters) only ever rise; they measure work done. peak_alive_tiles is a high-water mark.

Mass-balance identity Splitting inbound/outbound by direction is not cosmetic: across all classes, Σinbound − Σoutbound equals the net buffer flow between the pool and the fallback (positive = the pool drains the fallback via shrinks; negative = it bleeds into the fallback via grows). The gaps cross − Σinbound and cross − Σoutbound isolate reallocs whose destination/source was the fallback. Edge asymmetries are free self-checks — the smallest class can never receive an inbound grow, so a non-zero there is a dispatch bug.
Correctness note — u64 fallback counters The fallback byte counters (fallback_bytes_alloc/dealloc) are u64, not usize. They are cumulative-over-lifetime, and on wasm32 a 32-bit usize would wrap past 4 GiB of accumulated fallback traffic — minutes of sustained churn. If one of the pair wrapped before the other, bytes_alive = saturating_sub(…) would collapse to 0 (or spike) and snap back, producing periodic minute-scale oscillation in the snapshot. u64 removes the wrap for all practical purposes.

8Stats output & tuning

TileAllocator::snapshot_stats() copies a handful of usizes per class into a plain stats struct, rendered two ways. Both return plain Strings and are auto-installed on window at module start (via wasm-bindgen), so they are callable straight from the DevTools console with no host wiring — the caller chooses the sink (console, clipboard, side-by-side diff). There is no AS3 surface. 

window.tilemallocTable()   // single-line, human-diffable snapshot
window.tilemallocStats()   // compact JSON, the stable machine-readable schema
window.tilemallocTrim()    // reclaim empty extents; returns bytes released

The single-line table is the one to reach for when eyeballing two snapshots:

tilemallocStats() emits the full JSON schema (per-class records + fallback + totals; histograms included only when ENABLE_HISTOGRAMS is on). The class order matches TILE_CONFIG; all values are non-negative integers.

9System memory introspection

The same pool counters back real implementations of Adobe's memory-introspection API, replacing the previous hard-coded stubs (which returned a fixed 10 MB / 90 MB / 100 MB regardless of actual usage). AS3 content — including Flex's own memory monitors and any diagnostic overlay — now reads truthful numbers. System.as declares them as native getters; AVM2 binds them to the Rust functions by the usual naming convention (get freeMemory → get_free_memory).

All four getters derive from two primitive measurements of the running module:

  • wasm_linear_memory_bytes() — the total size of the module's linear memory right now (memory_size(0) × 64 KiB). It grows monotonically via memory.grow; the WASM MVP has no shrink. This is the entire address space the module has obtained from the host.
  • heap_base() — the link-time __heap_base symbol from wasm-ld. Bytes in [0, __heap_base) are the fixed boot cost (statics + initial stack); bytes in [__heap_base, linear_memory) are dynamic heap actually served by tilemalloc and the dlmalloc fallback.
GetterFormulaMeaning
totalMemoryNumberlinear_memory − heap_basedynamic heap obtained (Number; no 4 GiB cap)
totalMemorytotalMemoryNumber as uintsame value, legacy uint API
freeMemorytotalMemoryNumber − (live_tile_bytes + fallback_live_bytes)allocated-but-unused heap; rises after System.gc()
privateMemorylinear_memorywhole linear memory incl. boot cost

Adobe added totalMemoryNumber precisely because totalMemory's uint overflows past 4 GiB; prefer the Number getters near the ceiling. On non-WASM (desktop) targets the two primitives return 0 and the getters degrade to 0 — tilemalloc isn't the global allocator there, so the counters wouldn't be meaningful anyway.

10wasm64 support

The 4 GiB ceiling of wasm32 is the real wall for these XML workloads, so the memory getters are written to survive a future wasm64-unknown-unknown build unchanged:

  • WASM_PAGE_SIZE and heap_base() are gated on target_family = "wasm", which matches both wasm32 and wasm64. The page size (64 KiB) and the __heap_base symbol are identical on both, by spec and by wasm-ld respectively.
  • wasm_linear_memory_bytes() has three arms: wasm32::memory_size (stable since 1.33), wasm64::memory_size (nightly simd_wasm64), and a non-WASM stub returning 0.
  • core/src/lib.rs carries one crate attribute, #![cfg_attr(target_arch = "wasm64", feature(simd_wasm64))], enabling that intrinsic only on the wasm64 target. It is inert on wasm32 and desktop (the predicate is false, so the pragma is never evaluated); Ruffle's wasm64 pipeline already builds with RUSTC_BOOTSTRAP=1.

On a wasm64 build these getters return real values instead of 0, with no other change. The rest of the allocator is pointer-width agnostic (size_of::<*mut ()>() drives the minimum tile size; everything else is in terms of usize/Layout).

11Measured impact

End-to-end, on a real enterprise application loading XML into a Flex data grid:

Workloaddlmalloc (stock Ruffle)TilemallocResult
~100,000-row XML into a data grid~30 s first load~15 s first load~2× faster
~250,000-row XML into a data griddid not finish — aborted after 5 min~40 sfrom unusable to practical
Per-GC cost (full cycle)heavy stutter, 100s of ms, grows with working setfast, flatdrastically lower
dataProvider refresh on repeated loadsdegrades as the working set growsstable / O(1) per opno slow creep

The 250,000-row case is the headline: without tilemalloc the load never completes in any reasonable time; with it the same document is in the grid in about forty seconds. That is not a micro-optimisation — it changes which documents the player can open at all.

The ~30 s → ~15 s gap shows up on the first load, against a fresh heap with no accumulated fragmentation — which isolates the cost: it is the per-malloc free-list work for hundreds of thousands of small tiles per cycle, not residual fragmentation from earlier loads. Tilemalloc serves each from an intrusive free list with a single pointer load and head rewrite. The faster GC follows from the same design: zero-coalescing frees, a regular cache-friendly heap layout, and a smaller working set with no fragmentation to sweep.

12Limitations & PR scope

  • Grow-only by default — extents reach a steady-state size and stay there (the point: no memory.grow churn); trim (§6) is the explicit, on-demand way to give a transient spike back.
  • Up-front footprint — ~160 MiB of pool address space if every class is touched, against wasm32's 4 GiB ceiling. Tune extent_mb / the class set per workload.
  • Single-thread only — unsafe impl Sync is sound only on the single-threaded WASM runtime; a wasm-threads target would need a Mutex.
  • Classes 1–3 bytes not representable — a consequence of the intrusive free list.
  • Config errors panic at module init (the config is validated the first time the allocator is used), rather than failing the build. A re-entrancy guard in ensure_initialized sets class_count before populating any class, so allocations that re-enter during bootstrap fall cleanly to the fallback instead of recursing.

The branch is self-contained for an upstream PR: a new tilemalloc/ directory (4 files) plus a handful of touched files, zero added AS3 surface (the System getters were already declared — only their bodies changed from stub to native), and no dependency on Ruffle's Flex/AVM2 leak-analysis instrumentation (which lives elsewhere and is out of scope). The nine instruments are part of the allocator and are not to be stripped before the PR — they measure only the tile pool and are what makes it tunable.

Key types

  • TileAllocator — the GlobalAlloc implementor; UnsafeCell-wrapped inner state, Sync on single-threaded wasm.
  • ClassState — per-class runtime: tile_size, tile_align, tiles_per_extent, free_head, the bump_ptr/bump_end carve cursor, the Vec<ExtentRecord>, and the counters.
  • ExtentRecord — one extent's ptr + total_bytes, plus the transient free_count/bucket scratch used only during a trim sweep.
  • FreeTile — { next: *mut FreeTile }, written into the first bytes of a free tile (hence size_bytes ≥ 4).
