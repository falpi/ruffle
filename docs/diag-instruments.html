This document describes the diagnostic instrumentation added on the diag-instruments branch. The instruments exist to investigate retention and leak patterns on long-running AVM2 workloads — they are not intended for upstream PR, and every change is gated as DIAGNOSTIC with explicit removal notes.

The investigation problem they were designed to answer is: "on a long session of an AVM2 application, why does memory plateau drift upward across load/unload cycles even when the display tree is bounded?". The Ruffle profiler shows raw allocation totals, but does not answer the domain question — which AS3 classes are alive, which objects are pinned by what, which dispatchers accumulate listeners that nobody removes. The instruments below close that gap.

The end-to-end workflow they enable is:

  1. Run the application normally; trigger AS3 System.gc() between reloads or on demand.
  2. From the browser DevTools console invoke window.dumpRuffle() (or from AS3 ExternalInterface.call("dumpRuffle")) to flush a snapshot of every counter as tracing::warn! lines on target: "ruffle_diag".
  3. When a specific class is suspected of being retained, invoke window.dumpRetentionPath("pkg::Class") to print every strong reference chain that reaches a live instance of it from a GC root.
  4. Compare snapshots taken at different points of the session.

The signal you are looking for is rarely growth in the raw totals; it is differential monotonic growth in counts that should be bounded by the application's reload cycle.

Design principles

All instruments adhere to a small set of shared principles. These are not incidental — each was the answer to a concrete failure mode encountered during the investigation.

  1. DIAGNOSTIC: comment prefix. Every modification — module, struct, field, function, comment block — begins with DIAGNOSTIC: and ends with an explicit "remove before the upstream PR" hint. This makes bulk cleanup mechanical: a single grep finds every site to revert.
  2. No mutation of observable AVM2 state. Counters and accessors are read-only. Triggers are atomics or mutex-guarded slots. Snapshots never call into AS3 (Script::init() is read for its already-stored globals, never Script::globals() which would lazily run the script initializer). The walker never mutates any object.
  3. Drop-based bookkeeping. Counters that need balance (alive instances, dispatch-list size) cannot rely on AS3 calling remove symmetrically — applications routinely leak listeners. Instead, a Gc<Sidecar> allocated alongside ScriptObjectData runs its Drop when gc-arena collects the parent, and the Drop decrements the counter. This guarantees alive = created − dropped without instrumenting any AS3 code path.
  4. Decoupled from force_full_gc. Applications routinely call flash.system.System.gc() from many sites — cleanup paths, finalizers, navigation events. Triggering dumps from inside the force_full_gc block would flood the log. Instead, the dump trigger is an explicit window.dumpRuffle() call from JS; the host decides cadence.
  5. Semantic edge labels, not pointer graphs. gc-arena exposes no generic heap visitor (Collect::trace takes an opaque context). The walker performs a semantic walk: per-type strong-edge extraction with human-readable labels (slot#N, dyn:propName, __proto__, loader-info.root, …). Output is a directly-readable chain root → … → instance rather than a pointer dump.
  6. tracing::warn! on target: "ruffle_diag". All dumps emit warn-level lines on a dedicated tracing target so they appear in the browser console without requiring trace-level subscription, and filter cleanly from the noisier WARN lines elsewhere.

Sidecar pattern: AliveTracker and DispatchSidecar

The hardest counters to keep balanced are the per-instance counters: alive count per class and dispatch-list size per receiver. Both must fire a decrement when the parent object dies, but there is no AVM2 hook "object collected" — gc-arena does not call user code on collection unless an object's Drop is registered. The solution is the sidecar pattern.

What it is

Inside ScriptObjectData (the data common to every TObject implementation) we embed two extra fields:

struct ScriptObjectData<'gc> {
    // … all existing fields …

    /// DIAGNOSTIC: alive counter sidecar.
    _alive_tracker: Gc<'gc, AliveTracker>,

    /// DIAGNOSTIC: dispatch-list bookkeeping sidecar.
    dispatch_sidecar: Gc<'gc, DispatchSidecar>,
}

Each sidecar is a separately allocated Gc<...> whose sole owner is the parent ScriptObjectData. When the parent is collected, the sidecar becomes unreachable, gc-arena calls Drop on it, and the Drop runs our decrement.

Why a separate Gc allocation and not a field with Drop

gc-arena requires Drop-bearing types to be #[collect(require_static)], which forbids them from holding any GC handle. ScriptObjectData itself holds many GC handles, so it cannot implement Drop directly. By extracting the drop responsibility into a separately-allocated Gc<Static>, we get:

  • AliveTracker and DispatchSidecar are #[collect(require_static)] and contain only String / HashMap<String, u32> — no GC handles.
  • They live in their own Gc allocations; gc-arena calls their Drop on collection.
  • They share their parent's lifetime exactly: 1:1 ownership, parent drops → sidecar drops.

AliveTracker

Records the death of an AVM2 instance. Created in ScriptObjectData::new and custom_new with the parent's class name; on Drop it calls diag_alive::record_drop(&self.class_name).

DispatchSidecar

A more elaborate sidecar that maintains a per-event-type counter of how many listeners are still attached to the parent (snapshot, not pointers). The hooks in event_dispatcher::add_event_listener and remove_event_listener keep this counter in sync. On Drop, DispatchSidecar:

  1. Calls diag_dispatch::record_drop once for the parent receiver, so the per-receiver entry is removed from the tracker.
  2. For every (event_type, count) still attached at collection time, calls diag_listeners::record_remove_str count times.

The second step is what corrects the otherwise-asymmetric add/remove counts in diag_listeners and diag_dispatch: if an application registers a listener and never removes it but the dispatcher itself eventually dies, the sidecar fires the symmetric removes at GC time, and the alive = adds − removes accounting balances. Without this, both telemetries are add-only and overcount alive listeners on high-churn but balanced workloads (e.g. components that recreate sub-component listeners on every rebuild).

Stable receiver identity

DispatchSidecar is also used as the stable identity of its parent in diag_dispatch's HashMap<(ptr, class_name), …>. The pointer returned by receiver_id() is self as *const _ as usize, which is stable for the entire lifetime of the parent (because the sidecar allocation is owned exclusively by the parent and outlives no longer than it does). This avoids two well-known traps:

  • Using a *const ScriptObjectData directly would not provide pointer stability across Gc::write operations.
  • Using a freshly-derived pointer at add_event_listener time would not match the pointer used by the Drop (which only sees the sidecar).

The sidecar pointer is stable, GC-safe, and equivalent on both sides.

Signature change propagation

Because ScriptObjectData::new now also takes the gc Mutation (to allocate the sidecars), the signature change has to propagate to every TObject implementation that constructs a ScriptObjectData. This touches ~30 files under core/src/avm2/object/ — the substantive change in each is just ScriptObjectData::new(class) → ScriptObjectData::new(class, mc). This is the bulk of the line-count delta on the branch and is mechanical.

Counter modules

Each counter module follows the same skeleton:

  • OnceLock<Mutex<HashMap<Key, Counter>>> for thread-safe lazy init.
  • record_add / record_remove (or record_create / record_drop) for hook calls.
  • dump_snapshot(top_n) returning a one-line String for tracing.
  • A previous-snapshot side table for delta computation across dumps.

The modules differ in their Key and what they aggregate.

diag_listeners

Purpose. See "alive listener" growth even when the AS3 display tree is bounded and AS3-side counters are flat — non-bubbling events from listeners on internal instances are invisible to stage-level counters.

Key: (class_name: AvmString, event_type: AvmString).
Value: { adds: u64, removes: u64 }. Alive = adds − removes.

Hooks: event_dispatcher::add_event_listener → record_add; event_dispatcher::remove_event_listener → record_remove; DispatchSidecar::drop → record_remove_str for every still-attached listener (the balancing pass).

Output: one line per dump.
RuffleListenerReg distinct_pairs=N total_adds=N total_removes=N net=N top_alive=[…] top_churn=[…]

  • distinct_pairs is the number of unique (class, event) keys observed
  • top_alive is the top-N keys by current alive count, with the explicit +adds/-removes(alive N) breakdown
  • top_churn is the top-N keys by adds + removes — useful to spot high-churn paths that are nonetheless balanced

diag_alive

Purpose. Spot zombie objects: AVM2 instances that are alive in memory but not reachable through the display tree. The discrepancy between alive and on-display counts is a direct measure of leak volume per class.

Key: String — the qualified class name (pkg::Local).
Value: { created: u64, alive: i64 }. i64 is intentional so an underflow is detectable (it would indicate a tracking bug).

Hooks: ScriptObjectData::new and custom_new → diag_alive::record_create(class_name). AliveTracker::drop (sidecar) → diag_alive::record_drop(class_name).

Output:
RuffleLiveAS3 distinct=N total_alive=N total_created=N top_alive=[Class=N(of M), …]

Class=N(of M) means N instances are currently alive out of M ever created. The ratio is informative: a class with N/M close to 1 is leaking; close to 0 indicates a transient class with normal churn.

Convenience accessor. alive_count_for(class_name) is used by the retention-path walker as a completeness check. It looks up by exact qualified name first; if missing, falls back to summing all entries whose key ends with ::<class_name>, so callers can pass a bare local name without qualification.

diag_dispatch

Purpose. Detect dispatch lists whose size grows reload-after-reload — the typical indicator of a long-lived receiver that accumulates listeners no one removes.

Key: (receiver_ptr: usize, class_name: String).
Value: { last_len: usize } — last observed total length of that receiver's dispatch list across all event types and priorities.

The receiver pointer can be reused by the allocator after a receiver is GC'd. This is acceptable noise: the per-class aggregation at dump time washes it out, and DispatchSidecar::drop calls record_drop before the pointer can be reused (because the sidecar Drop runs during GC, and the freed allocation cannot be handed out until after the sweep completes).

Hooks: event_dispatcher::add_event_listener → diag_dispatch::record_add(receiver_id, class_name, post_add_total_len); DispatchSidecar::drop → record_drop.

Output: TWO lines per dump.

Line 1 — broad top-N:
RuffleDispatchListSize receivers=N max_len=M top_class=[Class max=N(+Δ) avg=N count=N, …]

Line 2 — singleton-filtered, sorted by delta DESC:
RuffleDispatchListSize_Singletons receivers_count<=5=N top=[Class max=N(+Δ) count=N, …]

The second line is critical. Many large no-leak classes (e.g. the Stage itself, generic EventDispatcher) dominate the broad top by absolute size, hiding small but monotonically-growing singleton leaks (e.g. a manager singleton accumulating a handful of listeners per reload). By filtering to count <= 5 (true and quasi-singletons) and sorting by delta DESC, the second line surfaces those leaks immediately.

diag_roots

Purpose. Name the AVM2 classes whose instances a permanent dispatcher (e.g. the Stage) keeps alive through its listeners.

Inputs: an Object<'gc> known to be a permanent dispatcher.
Output: one RuffleRootListeners warn line per dispatcher.

For each handler in the dispatcher's dispatch list (DispatchList::diag_handler_targets):

  • Determine strong vs weak (HandlerRef::Weak stores a GcWeak).
  • For weak entries, upgrade() is attempted; failures are skipped (the listener is dead).
  • For surviving entries, extract the bound_receiver of the handler function via FunctionObject::executable().diag_bound_receiver().
  • Aggregate by (receiver_class, is_weak).

Output:
RuffleRootListeners <label> total=N strong=M weak=K top=[Class(S)=N, Class(w)=N, …]

(S) is a strong reference (the dispatcher pins the receiver via the listener); (w) is weak (does NOT pin). When investigating an orphan object whose retention root is unknown, scan the (S) entries for any class belonging to the orphan's expected sub-graph — that names the retention edge. (w) entries are shown for completeness, but understanding that they cannot retain is the whole point: this turns "a listener exists" into "a listener that retains" by reading the parenthesized tag.

diag_roots is called twice per dump from Player::dump_root_listeners_diag: once for the Stage, once for the root content of the running movie.

diag_xref

Purpose. Catch retention via a strong listener registered on an arbitrary (not necessarily permanent) dispatcher, where the handler's bound receiver is of a different class. This is the classic "long-lived singleton holds bound methods of short-lived components" pattern.

Key: (dispatcher_class: String, receiver_class: String).
Value: i64 — count, decremented on remove (floored at 0).

Hooks: event_dispatcher::add_event_listener → diag_xref::record_add(dispatcher_class, receiver_class); event_dispatcher::remove_event_listener → diag_xref::record_remove(dispatcher_class, receiver_class).

The hook in add_event_listener only fires when the listener is STRONG AND the bound receiver class differs from the dispatcher class. Weak listeners cannot retain, so they are irrelevant. Same-class self-registration is filtered out as noise (a component listening to itself does not indicate retention through a foreign edge).

Accuracy note. removeEventListener does not tell us whether the original registration was weak or strong. We decrement on every bound-method remove but floor at 0. This adds harmless noise to pairs that were correctly cleaned up; it never affects the leak signal, which is a strong listener that is never removed (so its counter only ever grows).

Output:
RuffleXref pairs=N top=[Dispatcher->Receiver=N(+Δ), …]

Direction note: Dispatcher → Receiver = N means the dispatcher class retains N instances of the receiver class via listeners. Reading the direction correctly is essential: a pair Component → FocusManager means the component retains the FocusManager (innocuous, since FocusManager is permanent); the inverse pair, if it grew, would be the leak indicator.

diag_unbound_caller

Purpose. When diag_roots flags <unbound>(S)=N strong listeners on the Stage (anonymous closures registered as stage.addEventListener("X", function(e){})), this instrument names the AS3 class containing the call site that registered them.

Why this matters: the unbound closure captures local scope, the strong listener keeps the closure alive, the captured scope keeps the surrounding instance alive. Anonymous closures on Stage are a common retention edge but diag_roots cannot say who registered them.

Key: String — the qualified caller class name.
Value: i64 — count of addEventListener calls observed.

Hook. In event_dispatcher::add_event_listener, when ALL of:

  • use_weak_reference == false (strong),
  • listener.executable().diag_bound_receiver().is_none() (unbound closure, not a bound method),
  • this.instance_of_class_name() == "flash.display::Stage",

we walk back the AVM2 call stack via Avm2::call_stack().borrow().frames() looking for the first frame whose method has a bound class. That class is the AS3 caller — the code path installing the closure — and we record it.

Output:
RuffleUnboundStageCaller distinct=N top=[Class=N(+Δ), …]

Trigger mechanism: diag_request

Both dump types are triggered by external requests from the JS host, not by internal events. The diag_request module holds the cross-thread shared state.

static DUMP_REQUESTED: AtomicBool = AtomicBool::new(false);
static RETENTION_REQUESTED: Mutex<Option<String>> = Mutex::new(None);

Dump request. request_dump_ruffle() (called from the JS-installed closure) sets the boolean to true. At the end of Player::update, take_dump_request() atomically reads-and-clears it; if true, the update calls dump_perf_diag and dump_root_listeners_diag.

Retention-path request. request_retention_dump(class_name) stores the target class name in the mutex. take_retention_request() takes it out at the end of Player::update; if present, the update calls avm2::diag_retention::dump_retention_paths.

The atomic boolean is enough for the dump request because it is parameterless. The retention request carries a class name, so it requires the mutex slot.

Why decoupled from force_full_gc. Earlier iterations triggered dumps inside the force_full_gc block (gated on AS3 System.gc()). Many applications call System.gc() from multiple sites per reload cycle, which flooded the log and made it impossible to distinguish a single observation point from the next. Decoupling moves the cadence decision to the JS host: invoke window.dumpRuffle() exactly when observation is wanted, and nothing fires otherwise.

Retention-path walker: avm2::diag_retention

This is the largest single instrument on the branch (~600 lines) and the most useful when the question is "who is keeping this orphan instance alive?".

Overall design

Given an AS3 class (qualified pkg::Local, or a bare local name), the walker does a breadth-first forward traversal of the AVM2 object graph starting from every enumerable GC root, following only strong semantic edges, and records every in-edge that reaches an instance of the target class.

For each match it prints the chain root → … → instance with per-hop labels and source classes. The BFS does NOT early-exit at the first match — it completes the whole reachable graph and records every in-edge into every target instance, so multiple independent retainers appear in a single run.

Why a semantic walk, not a pointer trace

gc-arena's Collect::trace takes an opaque &Collection context; it is designed for the collector itself, not for external observers, and cannot be re-purposed as a generic heap visitor. A pointer-level visitor would also produce nameless output ("root → 0x1234 → 0x5678 → target") that requires post-processing. The walker instead enumerates strong edges per type, with human-readable labels (slot#5, dyn:foo, __proto__, bound-method#3, …). The output reads like a call chain, not a pointer dump.

Roots enumerated

1. Stage display tree                       (root[stage])
2. ClassObject statics across all domains    (root[class:Name])
2b. Script global objects                    (root[script:Name])
3. Active Timer callbacks + parameters       (root[timer#N])
4. ExternalInterface.addCallback             (root[extcallback:'name'])
5. Player-held display object pointers       (root[mouse-hovered], etc.)
   - mouse_hovered, mouse_pressed, mouse_right_pressed, mouse_middle_pressed
   - drag_object
   - focus_tracker

Domains. Starts from Avm2::playerglobals_domain() and walks the Domain::children tree via Domain::diag_children. The DomainData::children field is normally gated behind #[cfg(feature = "egui")]; the diagnostic exposes it ungated so the walker can sweep movie/application domains in regular non-egui builds. For each domain, all (name, _ns, class) triples from Domain::classes() are seeded, and every ClassObject registered on each class is added as a root with label root[class:Name].

Script globals. Each package { … } block in AS3 produces a top-level Script whose globals are a regular Object<'gc>. A public var X = new ... declared at package level (not static inside a class) lives as a slot on the script global, not on a ClassObject. Without enumerating these, the walker would miss every cache stored in a package-level var — a common application-level leak pattern. The walker reads each script.init() (which returns (Method, Object, Domain) from the cached data without forcing lazy init) and adds the returned global as root[script:Name].

Script::init() vs Script::globals(). Diagnostics must NEVER mutate AVM2 state. Script::globals() runs the script's initializer on the spot if it has not run yet; Script::init() only returns the already-stored globals object (the slot is created when the script is loaded, before its initializer runs). The walker uses the latter.

__proto__ was the last-added edge and proved essential. For the vast majority of instances it points at ClassObject.prototype (already reachable as root[class:Name].prototype) and is a no-op for retention. But AS3 code can rewrite instance.__proto__ to chain unrelated objects (the proto chain), creating a strong edge gc-arena traces but a plain slot/dyn enumeration would miss.

The trait-name suffix on slot#N:<traitName> and bound-method#N:<methodName> is resolved by lookup_slot_name(obj, N) / lookup_method_name(obj, N), which linearly scan obj.vtable().resolved_traits() for the entry whose Property::Slot { slot_id } / Property::ConstSlot { slot_id } / Property::Method { disp_id } matches. Linear scan is acceptable: trait maps for typical Flex classes are O(100) entries and the walker is on-demand, not on a hot path. Resolution failure is silent (label falls back to the bare numeric form) so the dump is never broken by a missing trait.

Edges intentionally NOT traversed

The header line lists skipped=[LoadManager, EventObject-native, Sound/NetStream/Socket, AVM1, E4X-internals]. The rationale per category:

  • Weak edges (weak Dictionary keys, weak DispatchList handlers, the weak broadcast lists, the orphan list) do not retain. Their presence does NOT pin the target, so traversing them would only produce noise. (Values of weak-keyed Dictionary entries ARE traversed: they are strongly held until the entry is pruned.)
  • E4XNode internals. XML subtrees (parent / children) cannot reference UI objects, and skipping them keeps tens of thousands of nodes out of the walk on XML-heavy workloads. Whole XmlObject wrappers are still visited (via their slot/dyn edges), but the internal E4X tree is not unfolded.
  • AVM1. Out of scope — this is an AVM2 retention analyzer.
  • LoadManager, EventObject-native, Sound/NetStream/Socket. These hold Rust-side resources rather than AVM2 graphs; their AVM2 facades are still reachable through normal edges, but their internal state is not.

BFS implementation details

The walker keeps:

struct Walker<'gc> {
    nodes: Vec<Node<'gc>>,              // spanning-tree nodes
    visited: HashMap<*const (), usize>, // pointer -> node index
    queue: VecDeque<usize>,             // BFS queue
    target_local: String,
    target_pkg: Option<String>,
    target_nodes: Vec<usize>,           // indices of nodes matching the target
    extra_in_edges: Vec<…>,             // in-edges into already-visited targets
    node_cap_hit: bool,
}
  • visited keys on raw pointer to deduplicate (the gc-arena allocation is alive throughout the walk, so the pointer is stable).
  • When a node is added that already exists in visited AND is a target, the call is treated as an extra in-edge: the spanning-tree parent stays as before, but the additional (from, label, target_idx) is recorded in extra_in_edges. At report time, all retainer in-edges are listed (spanning-tree edge + every extra) so multiple independent retention paths surface.
  • NODE_CAP = 4_000_000 guards against pathological graphs; it is generously above any observed live-object population.

Completeness check

The report's header compares targets_found against diag_alive::alive_count_for(target_class):

RuffleRetentionPath class=… alive=A visited=V roots=R targets_found=T retainers=N skipped=[…]

If T < A, the diagnostic prints an explicit "NO PATH FOUND" line indicating that the missing retainers hide in one of the non-enumerated categories. The skipped list in the header is the direct hint to the next investigation step. This completeness check is the difference between "walker found a path" and "walker exhausted the strong graph". The former is enough when a path is found; the latter is what tells you when the walker itself needs another edge category.

JS-side surface

Two functions are installed on window from web/src/lib.rs::global_init:

window.dumpRuffle()

window.dumpRuffle()    // returns true

Forwards to ruffle_core::diag_request::request_dump_ruffle(). Sets the atomic flag; Player::update consumes it on the next frame and emits all counter snapshots:

  • RufflePerf
  • RuffleListenerReg
  • RuffleLiveAS3
  • RuffleDispatchListSize and _Singletons
  • RuffleXref
  • RuffleUnboundStageCaller
  • RuffleRootListeners Stage
  • RuffleRootListeners Root

Returns true so AS3 callers (ExternalInterface.call("dumpRuffle")) can distinguish "function available" from "function missing" (the latter returns null).

window.dumpRetentionPath(className, maxRetainers?)

window.dumpRetentionPath("pkg::Class")            // returns true; default 30 retainers
window.dumpRetentionPath("Class")                 // bare local, default 30 retainers
window.dumpRetentionPath("pkg::Class", 100)       // print up to 100 retainers
window.dumpRetentionPath("pkg::Class", 0)         // 0 → fall back to the default (30)

Forwards to ruffle_core::diag_request::request_retention_dump(name, max). The optional maxRetainers argument caps how many retainer lines get printed; the BFS itself always completes, so the header counts (alive, visited, targets_found, retainers) are accurate regardless of the print cap — only the per-retainer detail lines are truncated. Passing 0 or omitting the argument falls back to diag_request::DEFAULT_MAX_RETAINERS (30).

Stores the request; Player::update consumes it on the next frame and runs the walker on a mutate_with_update_context closure. Output is RuffleRetentionPath … warn lines. Returns true for availability detection.

Installation pattern

The functions are installed in two equivalent ways:

  1. #[wasm_bindgen(js_name = "...")] exports — accessible directly on the wasm-bindgen namespace.
  2. As global window properties via js_sys::Reflect::set, with Closure::forget() to leak the closure for the lifetime of the module. This is what makes them callable from the DevTools console without any wiring on the host page, and from AS3 via ExternalInterface.call("dumpRuffle").

The browser console is the primary intended consumer. AS3 calls are useful for triggering a dump from within an integration test or a custom dev UI.

Output format reference

All diagnostic output is on tracing::warn! level with the target: "ruffle_diag" filter. In the browser console these appear as WARN lines.

RufflePerf

RufflePerf wall={ms}ms frames={N} renders={N} updates={N} \

RuffleRetentionPath

Header

RuffleRetentionPath class={QName} alive={A} visited={V} roots={R} \
 targets_found={T} retainers={N} \
 skipped=[…] (weak edges not traversed)

If T == 0:

RuffleRetentionPath NO PATH FOUND: alive={A} instance(s) are retained only via \
 a non-enumerated edge category (see skipped list) — extend the walker or \
 escalate to a gc-arena fork with trace recording

Body — overall grammar

One line per retainer (up to the per-call cap — defaults to DEFAULT_MAX_RETAINERS = 30, overridable from JS via window.dumpRetentionPath(name, maxRetainers)):

RuffleRetentionPath retainer#N: <chain> -[<edge-label>]-> TARGET(<class> @0x<ptr>)

A <chain> is the spanning-tree path from a GC root to the parent of the target. Its general form:

<root-label><class-label-0> -[<edge-label-1>]-> <class-label-1> -[<edge-label-2>]-> … -[<edge-label-k>]-> <class-label-k>

Hop 0 is a root (no arrow, just root[…] followed by the root node's class-label). Subsequent hops have the form -[<edge>]-> (<class>). If more than 30 retainers are found, the line … N more retainer edge(s) omitted is emitted at the end. The full graph is still walked — the cap is only on print output to keep one dump readable in the console.

Worked example

A real retention path (from a SmartTable workload):

RuffleRetentionPath retainer#23: root[class:FlexGlobals](class FlexGlobals)
   -[slot#0:topLevelApplication]-> (application)
   -[slot#59:_focusManager]-> (FocusManager)
   -[slot#10:focusableObjects]-> (Array)
   -[array[54]]-> (SmartTable)
   -[slot#158:visibleData]-> (Object)
   -[dyn:916603BF-33FA-F935-1886-BC0F00DF502A]-> (SmartTableItemRendererLight)
   -[slot#39:_data]-> TARGET(XML @0x16131d08)

Reading it left-to-right:

  1. Root: class:FlexGlobals — a static class object.
  2. slot#0:topLevelApplication — the application instance held by FlexGlobals.
  3. slot#59:_focusManager — the FocusManager assigned to the application.
  4. slot#10:focusableObjects — an Array of focusable components.
  5. array[54] — the 54th element, a SmartTable.
  6. slot#158:visibleData — a private SmartTable cache (the field we identified as the leak source).
  7. dyn:<UID> — the dynamic Object map keyed by item UID.
  8. (SmartTableItemRendererLight) — the item renderer that the cache maps to.
  9. slot#39:_data — the renderer's data property, pointing at the leaked XML.

The leak diagnosis falls out of the path itself: slot#158:visibleData names exactly which SmartTable field is keeping the renderer alive, and slot#39:_data names the renderer property that pins the XML.

Instrumentation hooks

The two file paths under core/src/avm2/ that carry instrumentation hooks at AVM2-event time (rather than just data definitions) are:

core/src/avm2/globals/flash/events/event_dispatcher.rs

Both add_event_listener and remove_event_listener are hooked. After the underlying dispatch-list operation completes:

  • add_event_listener fires:
    • diag_listeners::record_add(class_name, event_type)
    • dispatch_sidecar.record_listener_add(event_type) — keeps the sidecar's per-event-type counter in sync
    • diag_dispatch::record_add(receiver_id, class_name, total_len) — using the sidecar's pointer as the stable receiver identity
    • diag_xref::record_add(dispatcher_class, receiver_class) — only when STRONG and the receiver class differs from the dispatcher
    • diag_unbound_caller — only when STRONG and unbound and the dispatcher is flash.display::Stage; walks the AVM2 call stack to name the AS3 caller class.
  • remove_event_listener fires:
    • diag_listeners::record_remove(class_name, event_type)
    • dispatch_sidecar.record_listener_remove(event_type)

The hooks are all-purpose: they fire for every listener, whether the result is interesting to the investigation or not. Filtering happens at dump time, not at hook time. This keeps the hook path cheap.

core/src/avm2/events.rs

The DispatchList type itself gets two diagnostic accessors:

  • diag_total_len() — sum of handler counts across all event types and priorities, used by diag_dispatch to record post-add total length.
  • diag_handler_targets(mc) — returns Vec<(is_weak, FunctionObject)> with dead weak entries already skipped, used by diag_roots and the retention-path walker.

Caveats and limitations

  • The walker is a forward strong-edge reachability analyzer, not a reverse-lookup tool. It cannot answer "who retains object X" by pointer — only by class name. To investigate a specific instance whose class is shared by many siblings, the dump must be reviewed manually to find the one whose retention edge looks anomalous.
  • The walker covers strong AVM2 edges only. Rust-side strong references that gc-arena traces but the walker does not enumerate (e.g. a future SoundChannel field added to Avm2 that holds an Object) will produce a targets_found < alive mismatch. The completeness check makes this explicit, but resolving it requires extending the walker.
  • The accuracy of diag_xref removes is approximate by design: removeEventListener does not differentiate weak vs strong registration. The counter is floored at 0, so harmless noise on balanced pairs does not affect the leak signal (only "never removed" pairs grow monotonically).
  • diag_unbound_caller only fires for Stage. By construction it is intended to attribute the well-known <unbound>(S)=N pattern on Stage. Extending it to other dispatchers is straightforward but was not needed for the investigation.
  • diag_dispatch's per-receiver entry uses (pointer, class_name) as key. Pointer reuse after collection is handled by DispatchSidecar::drop calling diag_dispatch::record_drop before the pointer can be handed to a new allocation; this is correct under gc-arena's collection model but would need re-checking under any alternative allocator.
  • The dump output is one line per snapshot per counter and has a top-N cap. For the per-frame counter dumps the cap is hard-coded at the call sites in Player::dump_perf_diag. For the on-demand RuffleRetentionPath, the cap is per-call parameterizable via window.dumpRetentionPath(name, maxRetainers) — the BFS still completes, only the printed retainer lines are truncated, so header counts stay accurate regardless of the cap.
  • The branch is not meant for upstream PR. It is the consolidated artifact of an investigation. The actual fixes derived from this work go on fix-memory-leaks (the 5 upstream-ready fixes the branch is built on) and on tile-memory-allocator (the tilemalloc allocator, a separate PR-ready branch). The diagnostic instrumentation here is intentionally disposable.
